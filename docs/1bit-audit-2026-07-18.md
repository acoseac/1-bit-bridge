### B1 — `parseReplayGain` accepts NaN/±Inf, silently dropping up to 500 tracks per bad tag, permanently — **High** — `internal/manifest/extractors.go:1104`

`parseReplayGain` does `v, err := strconv.ParseFloat(s, 64); ... return &v` with **no finiteness guard**. `strconv.ParseFloat` accepts `"nan"`, `"inf"`, `"-inf"`, `"infinity"` with no error, so a ReplayGain tag of `"nan dB"` / `"-inf dB"` / `"inf"` yields `&NaN` / `&±Inf`. (Such values are emitted by real ReplayGain scanners for digital-silence / infinite-true-peak tracks, and by corrupt tags.)

**Traced failure chain (verified end-to-end):**
1. `populateFromTagMetadata` (extractors.go:611-617) sets `t.ReplayGainTrackDB = &NaN` (and/or `ReplayGainAlbumDB`), *tag*-derived — so the `replayGainFromAnalysis` provenance flag is **false**.
2. `marshalForStorage` (store.go:1497) scrubs `ReplayGainTrackDB` **only** when `replayGainFromAnalysis` is true, so the tag-derived NaN survives into `json.Marshal(&clone)` (store.go:1509), which returns `json: unsupported value: NaN`.
3. `UpsertTrackBatch` does `raw, err := marshalForStorage(t); if err != nil { return err }` **before `BeginTx`** (store.go:1851) → one poisoned track aborts the whole batch with zero SQL.
4. `runScanWriter.flush` logs the error then unconditionally `batch = batch[:0]` (scanner.go:928-938; docstring: "partial rows are lost but the scan continues") — no per-track fallback, no retry. **All up-to-`scanBatchSize`=500 tracks in that batch are discarded.**
5. The tag never changes, so every rescan re-poisons whatever batch the track lands in → those tracks are permanently absent from the manifest (and thus from iOS delta-sync + enrichment).

The author already guards this **exact** failure in the sibling parser: `parseAIFFExtended` (extractors_aiff_wav.go:230) has `if math.IsInf(val, 0) || math.IsNaN(val) { return 0 }` with the comment *"A ±Inf / NaN SampleRate would fail json.Marshal when the Track is persisted, breaking the whole tags_json batch write."* `parseReplayGain` is the one float-from-tag parser missing the guard.

*Fix sketch:* in `parseReplayGain`, before `return &v`, add `if math.IsInf(v, 0) || math.IsNaN(v) { return nil }` (mirrors `parseAIFFExtended`; add the `math` import to extractors.go if absent). Consider also making `runScanWriter.flush` fall back to per-track upsert on batch error so one bad row can't take 499 good ones down.

### B2 — `deviceSeen` device-registration debounce map grows unbounded (no reaper / cap / TTL sweep) — **Low** — `internal/api/api.go:161`

`touchDevice` writes `s.deviceSeen[deviceToken] = …` on every successful device-registration upsert (api.go:562) and the entry is **never** deleted — no reaper goroutine, no size cap, no TTL sweep. The `deviceRegistrarTTL` (5m) only gates whether a *re-upsert* fires (the `fresh` check at :501); it never evicts. The sibling `deviceInflight` map IS cleaned (deferred `delete` at :533), and the two analogous caches in the same package deliberately self-bound (`pairingRateLimiter`: 10k cap + hourly GC; `manifestRateLimiter`: idle reaper). `deviceSeen` is the inconsistent outlier.

*Failure scenario:* `authed()` calls `touchDevice` for any request whose `X-Device-Token` passes `validDeviceToken` — which accepts **any** non-empty lowercase-hex string up to 128 chars (a huge key space, not just the one 64-char token a real client holds). An authenticated client (compromised paired device, leaked bearer, or a buggy client regenerating its device token per request) that rotates `X-Device-Token` adds one permanent entry per distinct value → slow unbounded memory growth toward OOM. Only active when a `DeviceRegistrar` is wired (the production playlist/history path). *Mitigations (why Low):* auth-gated (not a bypass — the token boundary holds); the single-user model means a conforming iOS client sends exactly one stable token (~1 entry/device).

*Fix sketch:* bound `deviceSeen` — a periodic reaper dropping entries older than `deviceRegistrarTTL`, or an LRU cap with oldest-eviction, mirroring `pairingRateLimiter` / `manifestRateLimiter`.

### B3 — DLNA Folders view orders intra-folder tracks by `AbsolutePath`, which is empty for UPnP-routed tracks → arbitrary order — **Low** (minor/cosmetic) — `internal/dlna/folder_index.go:264`

`BuildFolderIndex` derives the folder **hierarchy** from `RelativePath` when every track has it populated (`allRelativePathsPopulated`, :195), but sorts tracks **within** each folder by `AbsolutePath` (:263-264: `trackList[i].AbsolutePath < trackList[j].AbsolutePath`). UPnP-routed tracks (the "Chord 2Go as UPnP source" feature) are constructed with `AbsolutePath = ""` (the documented resolver-miss sentinel, cmd/bridge/dlna_wiring.go:528) but `RelativePath` populated.

*Failure scenario:* browse a UPnP-sourced library via the DLNA **Folders** axis. In a folder whose tracks are all routed, every sort key is `""`; `sort.Slice` (pdqsort, unstable) permutes them into an order that is neither track-number, filename, nor insertion order. In a *mixed* folder, all routed tracks (`""`) clump ahead of all filesystem tracks. Filesystem-only libraries are unaffected (AbsolutePath populated ⇒ path-order == filename-order within a folder). Not a crash/data-loss; pagination stays stable within a generation (`folderIndexCache` publishes one `*FolderIndex` per generation) — purely wrong ordering.

*Fix sketch:* sort by `RelativePath` (or fall back to `RelativePath` when `AbsolutePath == ""`), matching the same field the hierarchy is derived from.

### B4 — `bridge upscale --gc` / `optimize --gc` mass-deletes the whole `track_variants` catalog when `variantsDir` exists-but-empty (cleanly-unmounted volume) — **Medium** — `cmd/bridge/upscale.go:680`

`gcCheckOutputDirBeforeReverseSweep` (the guard explicitly added in PR #207 to "not mass-delete rows on a disappeared transcoded root") refuses the reverse sweep only when `outputDir` is **missing** (`os.ErrNotExist`) or unstatable — but returns `0` (proceed) when it exists-but-empty:
```go
_, statErr := os.Stat(outputDir)
switch {
case statErr == nil:
    return 0 // Healthy state — proceed to the per-row loop.   ← empty dir passes here
case errors.Is(statErr, os.ErrNotExist): ... return 1
default: ... return 1
}
```
The reverse sweep (upscale.go:736-767) then `DeleteVariant`s every row whose `SidecarPath` (all under `outputDir`) returns `ErrNotExist`.

*Failure scenario:* an operator with `variantsDir` on a separate mount (network/external/rclone-FUSE — a supported config; the B2-bucket phantom-rows case in CLAUDE.md confirms variants can live on network storage). On Linux/macOS a **cleanly-unmounted** volume reverts its mountpoint to an empty *local* directory (the default unmount behavior — not a deleted dir), so `os.Stat(outputDir)` succeeds on an empty dir → guard passes → all sidecars appear `ErrNotExist` → **every `track_variants` row is deleted in one run**. The forward sweep runs first and reports "removed 0, kept 0" but that signal is never cross-checked. iOS loses every advertised variant; the bridge re-transcodes the whole library; worse, a *subsequent* `--gc` after remount sees the now-orphaned files (rows gone) and force-deletes the actual `.flac` sidecars. The guard misses its own stated purpose (its message even says "likely a disconnected mount").

*Fix sketch:* in `gcCheckOutputDirBeforeReverseSweep`, also refuse when `outputDir` is a directory, `rowCount > 0`, AND it's empty (`os.ReadDir` returns 0 entries) — an empty transcoded root with extant rows is the same "don't mass-delete" signal as a missing one. (Consider also honoring `--dry-run` on the `--gc` path, which is currently defined but silently ignored, and/or a typed-confirm gate like `artwork --gc`'s.)

### B5 — `AutoInstallRestart` calls `os.Exit(0)`, bypassing the graceful-shutdown cleanup the documented restart invariant requires — **Medium** — `cmd/bridge/main.go:1958`

CLAUDE.md line 47 is a hard invariant: *"The `POST /api/restart` admin handler MUST NOT call `os.Exit(0)` directly. It must invoke the same cancellation closure that handles SIGINT/SIGTERM. This ensures the `bgScans` WaitGroup is honored (preventing SQLite corruption), in-flight transcode jobs are cleaned up, and the `auth.Store` flushes its last-used-at debounce buffer."* The admin restart correctly uses the parent `cancel` (main.go:2709 `Restart: cancel`). But the functionally-identical auto-install restart trigger does:
```go
updOpts.AutoInstallRestart = func() {
    fmt.Fprintln(stdout, "Restarting after auto-install (service manager will respawn).")
    scanCancel()   // cancels only the scan CHILD ctx — never fires the parent ctx.Done() graceful branch
    os.Exit(0)     // skips every deferred cleanup
}
```
`scanCancel` (main.go:1731) is the scan child's cancel, not the parent `cancel` (main.go:1522), so the graceful `select { case <-ctx.Done(): … }` branch never runs, and `os.Exit(0)` skips all defers: `store.FlushLastUsed()` (lost debounced `LastUsedAt`), `upscalePool.Stop()` (orphaned in-flight `sox` + leaked partial `.tmp` sidecar), `adminCancel()` → `admin.Server.Serve` never waits on the `bgScans` WaitGroup (an admin-triggered background scan mid-write is abandoned — the exact SQLite-mid-write exit lines 47/136/393 warn about). Auto-install gates on `sessions.Inflight()` for *streams* only, so a scan/transcode can be running concurrently.

*Fix sketch:* replace `scanCancel(); os.Exit(0)` with `cancel()` (the parent cancel is in scope at :1958) — it still returns from `main` → process exit → service-manager respawn, but honors every deferred cleanup, matching the admin-restart path.

### B6 — cross-owner dedup strands an upscale/optimize batch in "running" forever — **Low** — `internal/transcode/pool.go:393` × `internal/transcode/batch.go:972`

`Pool.Enqueue` dedups on `spec.SourceLibraryRel + "|" + spec.VariantID()` (pool.go:374) — **no batch identity** — and returns `nil` on a hit (pool.go:393, indistinguishable from a real enqueue). The `Coordinator`'s `Submit` counts that `nil` as enqueued and records `RemainingIDs[path]`, but `OnJobComplete`/`OnJobFailed` (batch.go:972/1024) early-return on `batchID == uuid.Nil` and otherwise key strictly on the *completing job's own* `batchID`.

*Failure scenario:* a legacy per-track `POST /v1/upscale` for track X (spec built with no `BatchID` → `uuid.Nil`) claims `inflight[X|variant]` first. A folder `Submit` (batch A) then covers X at the same target; X's projection still shows `HasVariant==false` (the first job hasn't committed its row yet), so `Enqueue(X, batchID=A)` **dedups → returns nil → A counts it enqueued + sets `RemainingIDs_A[X]`**. The first job runs to completion → `OnJobComplete(uuid.Nil)` early-returns → A's `RemainingIDs[X]` is never cleared. If X was A's last outstanding path, `len(RemainingIDs)==0` never becomes true, so A sits `running` on the admin Jobs page **indefinitely** (skewing its ETA), cleared only by a process restart (`RecoverInterruptedBatches` is boot-only) or operator Cancel. Two overlapping folder `Submit`s of the same source+target produce the same strand. The transcode itself succeeds (the first job committed the variant) — only the batch-completion accounting strands, hence Low.

*Fix sketch:* have `Enqueue` distinguish "dedup'd, not owned by you" from a real enqueue (e.g. return a typed sentinel) so the Coordinator drops that path from `RemainingIDs`/`TotalFiles` instead of awaiting a callback tagged with a different owner's `batchID`.

### B7 — `bridge init --public … --force` re-run rewrites `bridge.yaml` then hard-exits 1 without reinstalling the service (partial state + misleading exit code) — **Low** — `cmd/bridge/init.go:335`

On a `--force` re-init where admin creds already exist, `cfg.Save(cfgPath)` runs (init.go:335, config **rewritten to disk**), then `store.MintInitial("admin")` returns `ErrAlreadyInitialised` → `return 1` (init.go:396-404) **before** `finishInit` (service install/reload). Net: the config change landed, but the exit code reads as total failure and the service is never reloaded to pick it up — the operator sees "failure" over a partially-applied change. No data loss (cert + creds preserved).

*Fix sketch:* check the existing-creds condition **before** `cfg.Save`, or treat `ErrAlreadyInitialised` as non-fatal on a `--force` re-init (skip the mint, proceed to `finishInit`).

### B8 — concurrent `Install` calls are unserialized and collide on deterministic scratch / `.bak` / binary paths → corrupt binary, destroyed rollback backup, or unverified-bytes TOCTOU — **Medium** — `internal/updater/install.go:103`

`Updater.Install` holds no install-in-progress lock (verified: `u.mu` is only taken for microsecond `Status()`/`recordDeferredReason` reads, never across the install; no `installMu`/atomic guard exists in `internal/updater`, `internal/admin`, or `cmd/bridge`). Every intermediate path is **deterministic** — `scratch = DataDir/updates` (install.go:173), `archivePath = scratch/<asset>` (:188), `extracted = scratch/bridge[.exe]` (:205), `swapBinary(BinaryPath, extracted, ".bak")` (:238) — plus `defer cleanScratch(scratch)` → `os.RemoveAll(scratch)` (install.go:177/329). Two callers can enter concurrently on the same instance with no serialization: the auto-installer poll (`maybeAutoInstall → u.Install`, updater.go:338) and the admin handler (`a.u.Install`), plus cross-process (a `bridge update` CLI vs the running bridge's auto-installer sharing `DataDir/updates/`).

*Failure scenarios (all guaranteed collisions on overlap, since nothing is per-attempt-unique):*
- **`cleanScratch` yanks the other install's files mid-flight** — install A returns (success/error) and `RemoveAll(scratch)` while install B sits between `Rename(dst, bak)` and `Rename(extracted, dst)` in `swapBinary` → B's `extracted` vanishes → swap fails source-missing.
- **Backup destruction** — both do `Rename(dst, bak)`; the second finds `dst` gone → errors, and both write `update-state.json` (last-writer-wins marker that may not describe the on-disk binary → wrong `DecideBootAction` next boot).
- **Verify/swap TOCTOU on the shared `extracted`** (worst case) — A extracts + `verifier(extracted)` **passes**, then B's `extractBridgeBinary` re-opens the same `scratch/bridge` with `O_TRUNC` and starts rewriting, then A's `swapBinary` renames `extracted → dst` — installing bytes A never verified (B's partial write). A corrupt binary at `dst` may fail to `exec` before `maybeRollbackOnBoot` runs → **unbootable bridge** until manual recovery.

Trigger requires two overlapping install invocations — uncommon in steady state, but reachable via an admin "Install" double-click during a slow (~15 min) download, an auto-install poll firing mid-admin-install, or the CLI-vs-running-bridge case.

*Fix sketch:* add an `Updater`-level install-in-progress mutex (`TryLock` → return "install already running" on contention), and/or give each attempt a unique scratch subdir (`os.MkdirTemp(DataDir/updates, "inst-*")`) so overlapping installs can't share `extracted`/`.bak`.

### B9 — `BrowseAll` early-terminates on a positive-but-understated `TotalMatches`, contradicting the code's own stated distrust of it — **Low** — `internal/upnp/pager.go:46`

`NextStartingIndex` stops iteration when `totalMatches > 0 && current+numberReturned >= totalMatches` (pager.go:46), so `BrowseAll` (client.go:135-143) breaks and returns its partial items with `err == nil`, `Truncated == false`. But the loop's own comment (client.go:105-107) states *"We already distrust `TotalMatches` for the sibling MiniDLNA 'inaccurate count while the DB builds' quirk"* — which is **false**: the `MaxBrowseAllItems` ceiling + empty-page terminator only guard the *over*-stated / stuck direction; a positive *under*-stated `TotalMatches` is trusted as an authoritative stop.

*Failure scenario:* an upstream that serves pages larger than its claimed `TotalMatches` with more data beyond (a MiniDLNA mid-DB-build inconsistency) — `NextStartingIndex(0, 200, 100)` → stop → `BrowseAll` returns 200 items with `err==nil`, the walk finishes non-truncated, and per the ingest contract a clean non-truncated walk is authoritative → the reconcile sweep reaps the un-fetched tail (silent). *Caveat (why Low):* the realistic MiniDLNA under-count case (server serves exactly what it counts) is transient reap-then-readd churn, not permanent loss; the *un-fetched-tail* loss needs the exotic "pages larger than the claimed total" server. Still worth reconciling because the code's own comment claims a distrust the termination path doesn't honor.

*Fix sketch:* drop the `TotalMatches` early-stop in `NextStartingIndex` and rely solely on the empty-page terminator (already present) + the `MaxBrowseAllItems` ceiling — this aligns the code with its stated "distrust `TotalMatches`" intent at the cost of one extra (empty) round-trip per container.

### B10 — booklet availability-check re-burns the attempt cap on a partial-chunk failure, collapsing the ~2-day budget to ~8 min and hammering Atlas — **Medium** — `internal/atlasharvest/booklets.go:110`

`checkBooklets` bursts chunked POSTs (500 MBIDs/chunk) with **no inter-chunk pacing** and aborts on the first failing chunk (`return err`, booklets.go:112). Each processed miss burns one attempt (`UpsertBookletAvailability(mbid, false, …)`, :143). The 6h-cadence stamp is written **only** on full success or endpoint-missing (`if err == nil || errors.Is(err, errBookletEndpointMissing) { SetLastBookletCheck }`, client.go:222) — so a partial failure leaves `LastBookletCheckAt` unset, and `bookletsCheckDue` re-runs the whole cycle on the next **60 s** tick.

*Failure scenario:* a >500-album library (≥2 chunks) against a rate-limited Atlas (the code's own comments cite "Atlas's per-source rate limit"). Chunk 1 succeeds — burning one attempt on every not-yet-available release in it; chunk 2 gets a 429 → `checkBooklets` aborts → no stamp. Next 60 s tick: `BookletsToCheck` still returns chunk 1's releases (attempts `1 < 8`), re-POSTs them (burns attempt 2), chunk 2 429s again. After ~8 ticks (~8 min) chunk 1's releases hit `maxBookletCheckAttempts=8` and are **permanently** skipped — defeating the documented design (booklets.go:56-60: 8 attempts × 6h ≈ 2 days "enough for Atlas's name-match ingest to link a freshly submitted library"). Any booklet Atlas links after the collapsed 8-min window is missed until a library rescan re-mints the MBIDs; meanwhile Atlas is re-POSTed chunk-1 every 60 s (the opposite of the intended polite pacing).

*Fix sketch:* stamp `SetLastBookletCheck` even on a partial (non-auth) failure so the 6h cadence holds and completed chunks aren't re-burned (or track per-chunk completion so a retry resumes at the failed chunk); add inter-chunk pacing to reduce the 429s.

### B11 — service-install escapers leave `%` (Windows cmd) and `$` (systemd ExecStart) unescaped → an operator install path containing `%VAR%`/`$VAR` is env-expanded into a wrong `--config`/binary path — **Low** — `internal/packaging/packaging.go:323` (+ `:289`)

Two real-but-low-likelihood escaping gaps, both triggered only by an operator-chosen `--dir` containing a `%NAME%` or `$NAME` pattern (legal NTFS/ext4 filename chars; default LOCALAPPDATA/PROGRAMDATA paths never contain them):
- **`CmdEscape` (packaging.go:323)** escapes `"`/CR/LF/NUL but **not** `%`, and its docblock (:312-315) falsely asserts *"The only thing that can tear a double-quoted argument is a literal `"`"* — cmd.exe expands `%VAR%` **inside** double quotes. So the generated `1-bit-bridge.cmd` (Startup launcher) and `SpawnDetached`'s `cmd.exe /c` line env-expand a `%TEMP%`-style path segment → wrong `--config` → auto-start silently fails to come up. The sibling `systemdEscape` **does** double `%`→`%%` (knowing it's dangerous), so the codebase is internally inconsistent.
- **`systemdEscape` (packaging.go:289)** escapes `\`/`"`/`%`/CR/LF/NUL but **not** `$`. systemd applies `$FOO`/`${FOO}` substitution to ExecStart argv words *after* unquoting (double quotes don't suppress it; a literal `$` must be `$$`), so a `$data`-containing binary/config path is expanded (undefined → empty) → wrong path, while `bridge init` reports success. **#481 nuance:** commit #481 explicitly declined the *uniform* `$$` escape (correctly — `$$` would corrupt a literal `$` in `WorkingDirectory`/`StandardOutput`, which don't do `$`-expansion); the residual here is that the *targeted* fix (escape `$` only in the ExecStart `BinaryPath`/`ConfigPath` fields) wasn't applied. Neither case is test-covered (`packaging_test.go` pins only the `"`→`""` case).

*Fix sketch:* double `%`→`%%` in `CmdEscape` (batch-file literal-percent) and correct its docblock; add a field-specific `$`→`$$` escaper applied only to the systemd ExecStart `BinaryPath`/`ConfigPath` (not the uniform escaper #481 rejected).

## Quick wins

_Small, low-risk improvements (clarity, minor efficiency, robustness) with no behavior-change risk._

### QW1 — `generatePassword` docstring cites a 55-char alphabet; it's actually 57 — `internal/adminauth/store.go:411`

The `generatePassword` comment (store.go:416–425) states a "55-character alphabet", `256 % 55 = 36`, "discard any byte ≥ 220 (the largest multiple of 55 below 256)", and "≈ 92 bits of entropy". `passwordAlphabet` (store.go:414) actually has **57** characters (verified: 24 upper + 25 lower + 8 digits; only `I O l` and `0 1` are excluded, not `i o`). The **code is correct** — it derives `limit := byte(256 - (256 % int(alphabetLen)))` = 228 and takes `b[0] % alphabetLen` dynamically, so rejection sampling stays unbiased regardless of the count — but every constant in the comment is wrong for 57 (`256 % 57 = 28`, limit `228`, ~93.3 bits).

*Why it's worth fixing:* a maintainer "simplifying" the loop to the commented constants would hardcode `limit = 220`, which for a 57-char alphabet re-introduces modulo bias (bytes 220–227 would be accepted and `% 57` maps them onto the first 8 alphabet chars). Comment-only change; no behavior impact today.

*Fix sketch:* update the docstring to 57 chars / `256 % 57 = 28` / "discard ≥ 228" / "~93 bits".

### QW2 — stray placeholder comment before the `Server` struct (trivial/cosmetic) — `internal/tsnet/tsnet.go:20`

Line 20 is `// ... rest of the struct definition ...`, sitting between the `import` block and the `ListenPacket`/`HTTP3TLSConfig` methods — and *before* the actual `Server` struct definition (line 85). It reads as if struct fields were elided, but nothing is missing (the struct is fully defined below). Looks like a reordering/editing artifact. Harmless but momentarily confusing to a reader scanning top-to-bottom.

*Fix sketch:* delete line 20 (and consider moving the two methods below the `Server`/`Config` type declarations for conventional Go ordering).

### QW3 — `RunSox` commits on a clean exit code with no length-complete gate (the `analyze` #449 truncation fix isn't mirrored) — `internal/transcode/transcode.go:736`

`RunSox` checks only the process exit code before renaming the `.tmp` FLAC into place (`transcode.go:736-754`). CLAUDE.md line 150 documents that **sox exits 0 on a truncated-but-openable source** (opens via the intact front STREAMINFO, decodes ~half, prints `LOST_SYNC`, exits 0) — which is exactly why `internal/analyze` was hardened (#449) to reject a decode shorter than 90% of the probed duration. The transcode path has no equivalent gate, so a truncated source at transcode time (e.g. an in-progress rclone-to-B2 upload — nonzero bytes, openable header) produces a half-length variant FLAC that gets committed with a `track_variants` row and served to iOS as a short-playing variant.

*Mitigating:* unlike the analyze sidecar, the variant row records `SourceMTimeNS`/`SourceSize`, and `finalizeAndEnqueue` treats an mtime/size mismatch as stale — so once the source finishes uploading and is re-scanned, the variant *should* regenerate (transient/self-healing, **if** the resolve/serve path honors that drift — not verified from within `transcode`). Hence a quick-win, not a bug.

*Fix sketch:* mirror the analyze length-complete gate — probe the source duration once and reject the rename when the produced FLAC's length is < ~90% of it (via `sox --i -D` on the output, or a frame-count check), so a truncated decode never commits.

### QW4 — enricher caches an artwork body with no image/MIME validation, then stamps the track enriched (permanent) — `internal/enrich/enricher.go:965`

`writeArtworkAtomicStream` (CAA / iTunes / Atlas-premium paths) and the Deezer buffered twin (`deezer.go:190`) accept any non-empty ≤20 MB HTTP-200 body as artwork — the only content guards are the size cap and `n == 0`; there is **no** magic-byte / `Content-Type` check that the bytes are an image. A stale-CDN-edge / fronting-proxy / truncated 200-with-non-image response (HTML/JSON error doc) is written to `<mbid>-<size>.jpg`; back in `enrichOne` that returns cached-ok → `t.ArtworkMBID` set → `MarkEnriched` stamps `enriched_at`. `ensureArtworkCached`'s only existence gate is `os.Stat(path) == nil` (size/content-blind), so the bogus file is a **permanent** cache hit served to iOS as a broken image, and the `WHERE enriched_at = 0` worker never revisits it (recovery needs an operator `ResetEnrichedMisses`). The comments at enricher.go:972-984 reason explicitly about the `n==0` and size-cap guards but are silent on content type — not a documented omission.

*Mitigating (why quick-win, not bug):* the four upstreams normally return proper 404s for misses, so a 200-with-garbage requires upstream/edge misbehavior — real but uncommon; server-side only (no captive-portal vector).

*Fix sketch:* before committing, validate the first bytes are an image — `bytes.HasPrefix(head, []byte{0xFF,0xD8,0xFF})` (JPEG SOI) or `http.DetectContentType(head)` starts with `image/` — uniformly across all four write paths.

### QW5 — `EffectiveVariantsDir` docblock falsely claims the path "has already been vetted" — the default branch never is — `internal/config/config.go:1148`

The docblock (config.go:1148-1151) states: *"Validation (must be absolute, must not be under a library root) lives in `Config.Validate` … by the time this helper is called, the path has already been vetted."* But `Validate` checks only the raw `c.Upscale.VariantsDir` field, and `validateVariantsDir` short-circuits on empty (`if variantsDir == "" { return nil }`) — so when the field is empty, the returned **default** (`filepath.Join(dataDir, "transcoded")`) is *never* validated against the library roots. (Asymmetry: an *explicit* `variantsDir` under a library root is rejected, but the byte-identical *default* is accepted.) No live failure today — the "mystery audio files in a scanned root" tangle is defended by PR #475's anchored variant-sidecar filename exclusion — but the false "already been vetted" claim could lead a future contributor to skip an effective-dir containment check if that downstream defense is ever changed.

*Fix sketch:* either make `Validate` check `EffectiveVariantsDir(c.DataDir)` instead of the raw field, or correct the docblock to state the default branch is unvalidated (and why it's safe — the PR #475 exclusion).

### QW6 — auto-install `Sessions.Inflight()` gate isn't re-checked before the disruptive restart — `internal/updater/updater.go:352`

The `Tracker` exists to "refuse to swap-and-restart while a download is in flight" (sessions.go:8-19), but `Inflight() > 0` is checked only at install *entry* (updater.go:332, install.go:108) — before the download→verify→swap sequence whose download phase can legitimately take ~15 min on the ~30 KB/s worst-case link the code designs for. `maybeAutoInstall` then fires `autoInstallRestart()` (updater.go:352) with no final `Inflight()` re-check. So a download that *starts* during the install's own multi-minute window is dropped by the restart — exactly the mid-track DSD restart / Hugo-2 DoP-lock-loss the tracker's doc says it prevents.

*Fix sketch:* re-check `Sessions.Inflight() == 0` immediately before `autoInstallRestart()` (defer the restart to the next poll if a stream started).

### QW7 — UPnP `BrowseFoldersWalk` has no ceiling on Browse round-trips (breadth) or non-audio items — `internal/upnp/walker.go:189`

The walk bounds recursion via `MaxDepth=12` (walker.go:186) and yielded-audio-items via `MaxItems` (:204), but has **no** per-walk budget on containers/Browse HTTP round-trips (`stats.Containers++` is counted, never checked) and `MaxItems` counts only *audio* items — a container of ~100k non-audio rows (just under `MaxBrowseAllItems`) is fully iterated with `stats.Items` staying 0. So a wide-but-shallow (≤12) or cyclic-with-fanout container tree drives an effectively unbounded number of serial Browse round-trips while `MaxItems` never trips, hanging the ingest and hammering the upstream. Pure object-ID cycles + deep chains ARE caught (depth cap); breadth is not — defense-in-depth gap, not an active bug on the intended acyclic-filesystem MiniDLNA/2Go tree.

*Fix sketch:* add a per-walk container/round-trip budget (e.g. `stats.Containers >= MaxContainers → ErrWalkTruncated`) so a pathological/hostile upstream can't hang the ingest. (Related minor: `walker.go:246`'s empty-title fallback checks the *raw* trimmed title, so an all-control-char title sanitizes to `""` → path collapse/collision → silent trackID overwrite; re-check the *sanitized* output for empty. Very pathological trigger.)

### QW8 — a single >4 MiB Atlas results page permanently wedges the whole bio/description delta-sync — `internal/atlasharvest/client.go:520`

`pollResults` decodes every response through one shared `io.LimitReader(resp.Body, 4<<20)` (client.go:520). Result pages carry up to `resultsLimit` (default 200) items each with `bio`/`bioSummary`/`description` free-text (Wikipedia/Last.fm/TADB). If one page serializes past 4 MiB, `LimitReader` truncates it, `json.Decode` fails, and `pollResults` returns **before** `SetCursor` advances (client.go:466) — so the next tick re-requests the identical `since=<cursor>` page, truncates identically, and fails forever. Every later result for the whole library is blocked behind that one oversized page, with no self-heal (contrast the deliberate "cursor stuck on a full page" guard at client.go:477, which only fires on a *successful* decode). Uncertain trigger (depends on Atlas's actual bio lengths — typical pages stay well under 4 MiB), but a total silent non-self-healing halt if hit.

*Fix sketch:* on a decode failure that hit the size cap, halve `ResultsLimit` and retry (forward-progress escape), and/or raise the cap for the results endpoint specifically.

### QW9 — `clamp01` passes NaN through → a non-finite loudness would abort the *entire* smart-playlist regeneration (latent — trigger currently fenced off) — `internal/smartplaylist/energy.go:97`

`clamp01` (energy.go:97-105) handles `±Inf` (`+Inf→1`, `-Inf→0`) but lets `NaN` fall through (`NaN < 0` and `NaN > 1` are both false). If a `NaN` `ReplayGainTrackDB` reached `EnergyEnvelope`, it would survive into the persisted `Energy []float64` (the `variance < floor` sanitizer also fails open on NaN), and `smartplaylistgen/generate.go:358`'s `json.Marshal(g.Energy)` returns `json: unsupported value: NaN` → `Regenerate` aborts → **zero** smart playlists written for all devices. **Currently latent:** every writer feeding `ReplayGainTrackDB` blocks non-finite — analysis via `replayGainFromLUFS` (rejects NaN/Inf) and tags via `marshalForStorage`→`json.Marshal` (rejects NaN). This is the fenced-off twin of **B1** (`parseReplayGain`, which produces the NaN but can't persist it today). Worth a one-line hardening because the blast radius is total-feature-outage and a future `tags_json`-without-`json.Marshal` path or an in-engine `(albumGain+trackGain)` average (`+Inf + -Inf = NaN`) would re-open it.

*Fix sketch:* in `clamp01` add `if v != v { return energyMidpoint }` (or reject NaN in `EnergyEnvelope`), mirroring the `±Inf` handling already present.

## Larger refactors

_Structural changes worth their weight; noted for planning, not immediate action._

**None identified.** Every bug and quick win above is a localized, low-diff fix (a missing guard, a wrong comment, an unserialized call, an over-trusted count) — none stems from a structural or architectural problem. The package boundaries are clean and consistently applied (pure-helper + collaborator-type factoring, the wire-DTO discipline, the writer-mutex + streaming-scan conventions), the platform-specific code is properly build-tagged, and the concurrency primitives (SPSC rings, `sync.Once` guards, singleflight, atomic cursors) are used correctly throughout. A few *recurring* micro-patterns are worth a one-time sweep rather than a refactor: (a) the **NaN/±Inf-into-a-persisted-float** hazard appears in three places (B1 live, QW9 + smartplaylist latent) — a shared `finiteOrNil`/`finiteOr` helper at every tag/analysis float-parse boundary would close the class; (b) the **"partial failure leaves no completion stamp → retry re-does completed work"** shape recurs (B10 booklets, and the atlasharvest submit path benignly) — worth a consistent per-chunk-progress convention; (c) **env-expansion-safe escaping** for install artifacts (B11) deserves a single per-context escaper table with test coverage for `%`/`$`. All three are hardening sweeps, not restructurings.
