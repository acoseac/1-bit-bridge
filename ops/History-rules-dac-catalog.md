# Long form: the entries of `.claude/rules/dac-catalog.md`

> The long forms of `.claude/rules/dac-catalog.md`'s entries, written with it on 2026-11-17 (B730 B1). **These entries are still binding.** The rules file keeps each as one line ending `→ History-rules-dac-catalog.md`; the record, with the runs, the controls and both SHA-256s, is in `ops/engineering-log.md` under 2026-11-17.

## The catalog and its iOS projection (B730 B1)

- **A row with no USB match is iOS's alone: it carries `ios`, makes no claim only a match reaches (no identity line, native claim, timing, analogue or raw-maximum control), and matches no unit; a row gains a match only from a capture or a kernel quirk, which its identity line names.** Until B730 B1 the database held models with a capture or a kernel quirk alone, and a model with no capture stayed out of it (`ops/plan-b728-dsd-capability-design.md`, the identity section, amended there on the same day). The iOS registry's rows enter as profiles with `match: []`, which `Lint` allows only beside `ios` (a profile with neither is still "no match alternative"). A known unit plays native under `auto` with no clean answer and takes the row's timing (`internal/player/policy`, `policy.go`'s auto branch for a known DAC), so a guessed ID, or a match built from an iOS port name, would give another maker's DAC those decisions: the bridge matches by USB identity alone, and `Match` reads no name and no `ios` field. What only a match reaches (the identity claim and line, a native claim, the DSD prefill, the analogue and raw-maximum controls the DoP gain check passes over) has no meaning without one, so the lint refuses each on a row without a match, the controls inside `dop` included (`claimsOf` makes no identity claim for such a row). The QX13, whose USB identity has not been captured, ships as such a row; its schema-2 fixture (`testdata/qx13.json`, a placeholder vendor ffff) still shows the hidden-mode caveat on a matched model. **Don't give an iOS-only row a guessed ID or a match taken from a name, let `Match` read `ios` or compare a name, or put a claim only a match reaches on a row without one.** `TestAnIOSOnlyRowMatchesNoUnit` (the four captured units, a unit from every other alternative, and units whose product string is an iOS-only row's port name or token, under the placeholder vendor and the Hugo 2's IDs), `TestTheQX13CarriesItsHiddenModeCaveat`, `TestEveryClaimNamesItsProvenance` and `TestTheSchemaRefusesWhatItDoesNotDescribe` pin it.

- **DoP evidence is per rate: `heardBitRates` are the rates a listening heard, each heard itself (a heard rate says nothing of the rates below it, and the player reads it so), `refusedBitRates` the rates that failed (`refused`, `silence at`, `noise at`, `no frames at`), and the statement one of three (`stated DoP to`, `stated DSD to`, `stated no DSD`), each credited by its dop clauses both ways; in a row with `ios` every marker clause opens with its source's head and one clause credits each rate and the statement.** Schema 1 held `heardMaxBitRate`, and the player took every rate up to it as heard, which admits DoP under `auto` with no confirmation: once a failure may sit below a heard rate (iOS PR 1's per-rate evidence can say so), a maximum sends DoP where nobody listened. Schema 2 lists the heard rates, the lint refusing an unsorted or repeated list, and the player's one line reads the rate's own entry (`slices.Contains(p.HeardBitRates, bitRate)`); the refused-rate precedence and this box's clean override stay as they were. The at-or-below rule went with the maximum; a rate both heard and failed stays a contradiction, now over four failure markers (`noise at` and `no frames at` are new: a DAC that plays DoP as noise, and a rate no attempt's frames were taken at, iOS's lock proxy not reached). The statement is the maker's: `statedMaxBitRate` for a figure that says DoP, which the player's explicit `dop` counts as a claim and publishes at the `reported` rung, and `statedWithoutDoP` for a DSD figure that names no transport, or names native DSD (`{"kind": "dsd"}`), or a statement of no DSD (`{"kind": "none", "maxBitRate": 0}`), which the player never reads: the design had filed the Mytek's DSD256 as stated, and it would have sent DoP to a bound Mytek at DSD64 and DSD128 on the catalog's word (iOS PR 1 calls it `.dsdWithoutDoPStatement`). The Hugo 2's maker statement of DoP to DSD256 is recorded (the owner's answer to Q1, 2026-11-17), so for a bound Hugo 2 an explicit `dop` asks no confirmation and reads `reported` unless better evidence exists. The clauses are read rate by rate and both ways, so a list and its clauses cannot drift. In a row with `ios` the text after each marker clause's colon opens with its source's head, the kind (`submission`, `field log`, `maker`, `pcm ceiling`, `chip specification`, `retailer`: iOS PR 1's kinds, six in its table at iOS 6a1241eb) and a date where it has one, and one clause credits each rate and the statement, since the export reads the head alone as that entry's source. A DoP claim's source is its own registry row ("DACProfile.swift <row> at iOS <commit>"), a dated listening or a dated maker's document. A family row (`ifi.generic`) keeps its siblings' results in its sibling note and has no heard or failed rate of its own. **Don't read a heard rate as a maximum, file a DSD figure that names no transport as `statedMaxBitRate` (it is `statedWithoutDoP`, which the player never reads), credit a lock, a negotiation or a sibling's result as heard, put a family row's siblings' results in its own rates, or name a person in a source.** `TestEachDoPRateIsCreditedRateByRate`, `TestAFailureBelowAHeardRateIsKept`, `TestAStatementIsOneOfThree`, `TestAnIOSRowsClausesNameTheirSource`, `TestTheLegacyCeilingAgreesWithTheEvidence`, `TestNoEmbeddedDoPLineReadsAsAHearing`, `TestTheCapturedModelsAreSeededAsTheirEvidenceSays`, `TestAHeardRateAdmitsOnlyItself` and `TestAStatementWithoutDoPAdmitsNoDoP` pin it.

- **The export writes the rows with `ios` by `ios.order`, their legacy patterns and ceiling verbatim until iOS PR 3 retires them, deterministically, as its golden `DACCatalog.ios.json`, whose SHA-256 iOS PR 2 pins; it is held to the iOS registry's baseline the dispatch gave (`testdata/ios-registry-6a1241eb.json`, pinned by its SHA-256), never to itself.** Until iOS PR 3 the app's live matcher takes the first row in order whose patterns a port's name holds, so a reordered export would give a port another row's ceiling, IO buffer and cushion (`ifi.golink` sits ahead of `ifi.generic`), a raised ceiling would send DoP at a rate the unit failed, and a dropped pattern (`"KA3"`, `"TOPPING E30"`) moves resolution before PR 3. The export (`scripts/dac-profiles/ios-export`, package main) reads the embedded catalog and writes, for each row, what the app reads and nothing only the bridge reads (no USB ID, product string, native claim, bridge timing or control), spelled as iOS PR 1 spells it (`fieldLog`; `carrierRefused`, `heardSilence`, `heardNoise`, `noLockProxy`; `dop`, `dsdWithoutDoPStatement`, `noDSD`, `unrecorded`): rows by order, heard and failed entries by rate, other lists as written, two spaces, no HTML escaping, LF and one newline. `-check` writes nothing, exits 1 on a stale file and prints its SHA-256; CI's `dac-profiles` job runs it. The parity test reads the baseline, a dump of the live registry's objects at iOS 6a1241eb made before dispatch (an input, never derived from the catalog): every row in order and field by field, the legacy patterns and tokens compared after iOS's fold, which iOS applies at construction; the generic names; the live matcher's first hit for every name of iOS PR 1's corpus and its known siblings, with no exception (the export carries the legacy patterns), and for names two rows' patterns hold, by the baseline's rows; and the strict matcher over the export's keys, whose answers differ from the live ones exactly for the four names iOS PR 1 declares (`KA3`, `TOPPING E30`, `Brooklyn`, `Brooklyn DAC`). **Don't hand-edit the golden or the baseline, fix a parity failure anywhere but the catalog, order the rows otherwise, iterate a map unsorted, or export a field only the bridge reads.** `TestTheExportIsItsGolden`, `TestTheExportIsDeterministic`, `TestAnUnrecordedRowExportsNoEvidence` and `TestTheExportMatchesTheIOSBaseline` pin it.

- **The name keys are iOS PR 1's, printable ASCII, compared with A to Z folded: tokens of four characters or more; no token and generic name one inside the other; across two rows only, no token and the other's token or port name one inside the other; port names unique and none a generic name; no excluded token inside its own row's token; orders 1 to N, each once.** From iOS PR 3 on, a token a port's name holds is a DoP licence after first use, so a short, generic or shared token matches another maker's DAC: `KA3` (three letters, which the KA3's legacy pattern still is) is not the KA3's token, `FiiO KA3` is; `TOPPING E30` is the original E30's own name and no E30 II token; a token inside a generic name (`Combo384 Amanero`, `CX31993 HIFI AUDIO`, `Headphones`) would claim every board or chip that reports it. The cross-row rule reads distinct rows only: a row's own token inside its own port name (`qx13` in `FIIO QX13 `) is how that row matches. Port names are compared trimmed and folded for uniqueness, as iOS PR 1's own lint folds them, while the app matches one exactly, its case kept. Every catalog pattern, token, port name and generic name is printable ASCII, so Swift's `lowercased()` and the lint's fold agree on each. An excluded token rules a name out (`JM98MAX 2` keeps the JM98MAX 2 off the JM98MAX's row, `Lite` the E30 II Lite off the E30 II's), and one inside its own row's token would rule out the row's own names. **Don't seed a token from a legacy pattern (`KA3`, `TOPPING E30`), hold a row's own token against its own port name, or let a name outside printable ASCII in.** `TestTheIOSNameKeysLint` and `TestTheSchemaRefusesWhatItDoesNotDescribe` pin it.
