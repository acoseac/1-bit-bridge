> The long forms of `.claude/rules/dac-catalog.md`'s entries, written with it on 2026-11-17 (B730 B1). **These entries are still binding.** The rules file keeps each as one line ending `→ History-rules-dac-catalog.md`; the record, with the runs, the controls and both SHA-256s, is in `ops/engineering-log.md` under 2026-11-17.

## The catalog and its iOS projection (B730 B1)

- **A row with no USB match is iOS's alone: it carries `ios`, makes no claim only a match reaches (no identity line, native claim, timing, analogue or raw-maximum control), and matches no unit; a row gains a match only from a capture or a kernel quirk, which its identity line names. Its `ios` line names its own row of the registry at an iOS commit, or, for a row added past the registry's baseline, the dated wizard submission it came from (`ios: wizard submission <date>`, then the line's end, `, ` or ` (` and free text, which, as in every source, names no person and holds no email address), beside which its DoP claim cites no registry row (B944); which form a row names is held by the export's test alone (`iosLineProblems`, which reads the baseline), since the lint, which has none, takes either on any row.** Until B730 B1 the database held models with a capture or a kernel quirk alone, and a model with no capture stayed out of it (`ops/plan-b728-dsd-capability-design.md`, the identity section, amended there on the same day). The iOS registry's rows enter as profiles with `match: []`, which `Lint` allows only beside `ios` (a profile with neither is still "no match alternative"). A known unit plays native under `auto` with no clean answer and takes the row's timing (`internal/player/policy`, `policy.go`'s auto branch for a known DAC), so a guessed ID, or a match built from an iOS port name, would give another maker's DAC those decisions: the bridge matches by USB identity alone, and `Match` reads no name and no `ios` field. What only a match reaches (the identity claim and line, a native claim, the DSD prefill, the analogue and raw-maximum controls the DoP gain check passes over) has no meaning without one, so the lint refuses each on a row without a match, the controls inside `dop` included (`claimsOf` makes no identity claim for such a row). The QX13, whose USB identity has not been captured, ships as such a row; its schema-2 fixture (`testdata/qx13.json`, a placeholder vendor ffff) still shows the hidden-mode caveat on a matched model. Since B730 PR 2 the app builds its registry from this catalog's export, so a row can reach the catalog first, from a wizard submission, and no commit of the iOS registry then holds it as a row (2026-11-19, backlog B944: the Fosi Audio ZH3). An `ios` line of B1's one form, `DACProfile.swift <id> at iOS <commit>`, would name an iOS commit that does not hold the row, and the lint could not tell (`reIOSRef` asks only that the ID be the row's own and the commit look like one). The lint takes a second form, `ios: wizard submission <date>`, its date a real one, then the text's end, `, ` or ` (` and free text (`reSubmitted`, `submitted`), which may say what the projection's values rest on (the port name iOS reported, the PCM sweep, the volume answers, the clicks heard) and, as in every source, names no person and holds no email address; beside it the DoP claim cites no registry row either (`fromSubmission`), its source the dated listening. The lint has no baseline, so it takes either form on any row: a later change that rewrote a baseline row's `ios` line as a submission, its DoP claim moved to a listening, would lint clean, and so would a row added past the baseline citing a registry row at a commit that does not hold it. Which form a row names is held by the export's test alone (B944's second round): `iosLineProblems(base, profiles)` reads the baseline's rows and refuses a row of the baseline that names a submission and a row added past it that cites the registry, naming the row; `TestTheExportMatchesTheIOSBaseline` runs it over the catalog, and `TestTheBaselineDecidesWhichIOSLineARowNames` over four edited catalogs the lint takes, the KA17 rewritten as a submission and the ZH3 citing its registry row at iOS 3145606a refused, and their counterparts, differing in the form alone (the KA17 citing its own row at that commit, the ZH3 naming a submission on another day), passing. With the check inside the function deleted, exactly the two refusals go red (the round's control, in the B944 log entry). **Don't give an iOS-only row a guessed ID or a match taken from a name, let `Match` read `ios` or compare a name, put a claim only a match reaches on a row without one, cite an iOS commit that does not hold the row, or name a submission in the `ios` line of a row the baseline holds.** `TestAnIOSOnlyRowMatchesNoUnit` (the four captured units, a unit from every other alternative, and units whose product string is an iOS-only row's port name or token, under the placeholder vendor and the Hugo 2's IDs), `TestTheQX13CarriesItsHiddenModeCaveat`, `TestEveryClaimNamesItsProvenance`, `TestARowAddedPastTheRegistryNamesItsSubmission` (each form beside a DoP claim sourced to the listening; a submission with no date, a date that is none, a date run into its text or another kind; a submission whose free text holds an email address; a DoP claim citing the registry beside a submission), `TestTheExportMatchesTheIOSBaseline` (the lint cannot tell a row of the baseline from one added past it, and the export's test, which reads the baseline, can: a row of the baseline names its own registry row, a row added past it its submission), `TestTheBaselineDecidesWhichIOSLineARowNames` and `TestTheSchemaRefusesWhatItDoesNotDescribe` pin it.

- **DoP evidence is per rate: `heardBitRates` are the rates a listening heard, each heard itself (a heard rate says nothing of the rates below it, and the player reads it so), `refusedBitRates` the rates that failed (`refused`, `silence at`, `noise at`, `no frames at`), and the statement one of three (`stated DoP to`, `stated DSD to`, `stated no DSD`), each credited by its dop clauses both ways; in a row with `ios` every marker clause opens with its source's head, a `submission`'s and a `field log`'s with its date, and one clause credits each rate and the statement.** Schema 1 held `heardMaxBitRate`, and the player took every rate up to it as heard, which admits DoP under `auto` with no confirmation: once a failure may sit below a heard rate (iOS PR 1's per-rate evidence can say so), a maximum sends DoP where nobody listened. Schema 2 lists the heard rates, the lint refusing an unsorted or repeated list, and the player's one line reads the rate's own entry (`slices.Contains(p.HeardBitRates, bitRate)`); the refused-rate precedence and this box's clean override stay as they were. The at-or-below rule went with the maximum; a rate both heard and failed stays a contradiction, now over four failure markers (`noise at` and `no frames at` are new: a DAC that plays DoP as noise, and a rate no attempt's frames were taken at, iOS's lock proxy not reached). The statement is the maker's: `statedMaxBitRate` for a figure that says DoP, which the player's explicit `dop` counts as a claim and publishes at the `reported` rung, and `statedWithoutDoP` for a DSD figure that names no transport, or names native DSD (`{"kind": "dsd"}`), or a statement of no DSD (`{"kind": "none", "maxBitRate": 0}`), which the player never reads: the design had filed the Mytek's DSD256 as stated, and it would have sent DoP to a bound Mytek at DSD64 and DSD128 on the catalog's word (iOS PR 1 calls it `.dsdWithoutDoPStatement`). The Hugo 2's maker statement of DoP to DSD256 is recorded (the owner's answer to Q1, 2026-11-17), so for a bound Hugo 2 an explicit `dop` asks no confirmation and reads `reported` unless better evidence exists. The clauses are read rate by rate and both ways, so a list and its clauses cannot drift. In a row with `ios` the text after each marker clause's colon opens with its source's head, the kind (`submission`, `field log`, `maker`, `pcm ceiling`, `chip specification`, `retailer`: iOS PR 1's kinds, six in its table at iOS 6a1241eb) and a date where it has one, and one clause credits each rate and the statement, since the export reads the head alone as that entry's source. Of the six, a `submission` and a `field log` name their date in every head of the registry's baseline (27 and 1 sources at iOS 6a1241eb) and of the catalog (14 and 1 clauses at B1), and the lint refuses one with none (B730 B1's follow-up), so the export writes no such source without its date; a `maker` (12 in each at B1), a `pcm ceiling`, a `chip specification` and a `retailer` (1 in each) name none, and none is asked of them. The head binds the iOS form alone: in a profile without `ios` what follows a clause's colon is free text, which the lint reads no head from, so nothing there is held to a date. A DoP claim's own source is no head: it is its own registry row, a `listening` or a `maker`'s document, and the last two name their date in the ref (B1's rule), as a native claim's `capture` does, while the head kind `maker`, iOS's word for a maker's statement, names none. A DoP claim's source is its own registry row ("DACProfile.swift <row> at iOS <commit>"), a dated listening or a dated maker's document. A family row (`ifi.generic`) keeps its siblings' results in its sibling note and has no heard or failed rate of its own. **Don't read a heard rate as a maximum, file a DSD figure that names no transport as `statedMaxBitRate` (it is `statedWithoutDoP`, which the player never reads), credit a lock, a negotiation or a sibling's result as heard, put a family row's siblings' results in its own rates, name a person in a source, or ask a date of the four head kinds that carry none (`maker`, `pcm ceiling`, `chip specification`, `retailer`) or of a clause in a row without `ios`.** `TestEachDoPRateIsCreditedRateByRate`, `TestAFailureBelowAHeardRateIsKept`, `TestAStatementIsOneOfThree`, `TestAnIOSRowsClausesNameTheirSource`, `TestTheLegacyCeilingAgreesWithTheEvidence`, `TestNoEmbeddedDoPLineReadsAsAHearing`, `TestTheCapturedModelsAreSeededAsTheirEvidenceSays`, `TestAHeardRateAdmitsOnlyItself` and `TestAStatementWithoutDoPAdmitsNoDoP` pin it.

- **The export writes the rows with `ios` by `ios.order`, their legacy patterns and ceiling verbatim until iOS PR 3 retires them, deterministically, as its golden `DACCatalog.ios.json`, whose SHA-256 iOS PR 2 pins; it is held to the iOS registry's baseline the dispatch gave (`testdata/ios-registry-3145606a.json`, pinned by its SHA-256), never to itself, and a row or a known sibling added past the baseline to its declaration in the test (`additions`, B944): written by hand from the row's submission and its maker's figures, its rows after the baseline's, each name with both matchers' answers, the baseline's corpus replayed over the whole export.** Until iOS PR 3 the app's live matcher takes the first row in order whose patterns a port's name holds, so a reordered export would give a port another row's ceiling, IO buffer and cushion (`ifi.golink` sits ahead of `ifi.generic`), a raised ceiling would send DoP at a rate the unit failed, and a dropped pattern (`"KA3"`, `"TOPPING E30"`) moves resolution before PR 3. The export (`scripts/dac-profiles/ios-export`, package main) reads the embedded catalog and writes, for each row, what the app reads and nothing only the bridge reads (no USB ID, product string, native claim, bridge timing or control), spelled as iOS PR 1 spells it (`fieldLog`; `carrierRefused`, `heardSilence`, `heardNoise`, `noLockProxy`; `dop`, `dsdWithoutDoPStatement`, `noDSD`, `unrecorded`): rows by order, heard and failed entries by rate, other lists as written, two spaces, no HTML escaping, LF and one newline. `-check` writes nothing, exits 1 on a stale file and prints its SHA-256; CI's `dac-profiles` job runs it. The parity test reads the baseline, a dump of the live registry's objects at iOS 3145606a made before dispatch (an input, never derived from the catalog): every row in order and field by field, the legacy patterns and tokens compared after iOS's fold, which iOS applies at construction; the generic names; the live matcher's first hit for every name of iOS PR 1's corpus and its known siblings, with no exception (the export carries the legacy patterns), and for names two rows' patterns hold, by the baseline's rows; and the strict matcher over the export's keys, whose answers differ from the live ones exactly for the four names iOS PR 1 declares (`KA3`, `TOPPING E30`, `Brooklyn`, `Brooklyn DAC`). Since B730 PR 2 a row can reach the catalog before any registry holds it (2026-11-19, backlog B944: the Fosi Audio ZH3), while the baseline, an input never derived from the catalog, cannot grow with it, and the test held the export to its row count, its rows by place and its known siblings exactly, so any addition failed it. A row added past the baseline is held instead to its declaration in the test (`additions`, a `declared`), written by hand from its submission and its maker's published figures by the iOS procedure's rules (the iOS repository's `docs/DACProfilingWizard.md`, section 6), never from the catalog or the export, so the export is held to it as to the baseline; a declaration changes only with what it was written from. The parity (`parity`) keeps every check of the baseline (its SHA-256, its rows at their places, field by field, its generic names); takes past the baseline's rows the declared rows alone, in their order, field by field in the export's own shape, and no row beyond them; holds the catalog's known siblings to the baseline's, in its order, and then the declared ones; and replays the corpus over the whole export, the added rows included, since a row added last in order still takes a corpus name no earlier row holds (`FIIO KA1`, whose live answer is no row), which a replay over the baseline's rows alone would not see. Each declared name, the names a row's unit reported and its siblings, carries the answers both matchers must give it, and is replayed with the corpus. **Don't hand-edit the golden or the baseline, fix a parity failure anywhere but the catalog, order the rows otherwise, iterate a map unsorted, export a field only the bridge reads, take a declaration from the catalog or the export, or replay the corpus over the baseline's rows alone.** `TestTheExportIsItsGolden`, `TestTheExportIsDeterministic`, `TestAnUnrecordedRowExportsNoEvidence`, `TestTheExportMatchesTheIOSBaseline` and `TestAnAdditionIsHeldToItsDeclaration` (a fixture row declared past the baseline passes; undeclared, unexported, exported otherwise, put first, or with a pattern that takes `FIIO KA1`, it is refused, and so are a sibling listed but not declared, one declared but not listed, and one a row reaches) pin it.

- **The name keys are iOS PR 1's, printable ASCII, compared with A to Z folded: tokens of four characters or more; no token and generic name one inside the other; across two rows only, no token and the other's token or port name one inside the other; port names unique and none a generic name; no excluded token inside its own row's token; orders 1 to N, each once; and no known sibling (`iosKnownSiblings`) answered with a model row by the strict matcher, by a port name or by a token. A row added past the baseline keeps its names and every other row's apart both ways, its legacy patterns included, and no row reaches a sibling it brings, by a legacy pattern either (B944); the lint compares no legacy pattern across rows, so the export's test holds it (`namesApart`).** From iOS PR 3 on, a token a port's name holds is a DoP licence after first use, so a short, generic or shared token matches another maker's DAC: `KA3` (three letters, which the KA3's legacy pattern still is) is not the KA3's token, `FiiO KA3` is; `TOPPING E30` is the original E30's own name and no E30 II token; a token inside a generic name (`Combo384 Amanero`, `CX31993 HIFI AUDIO`, `Headphones`) would claim every board or chip that reports it. The cross-row rule reads distinct rows only: a row's own token inside its own port name (`qx13` in `FIIO QX13 `) is how that row matches. Port names are compared trimmed and folded for uniqueness, as iOS PR 1's own lint folds them, while the app matches one exactly, its case kept. Every catalog pattern, token, port name and generic name is printable ASCII, so Swift's `lowercased()` and the lint's fold agree on each. An excluded token rules a name out (`JM98MAX 2` keeps the JM98MAX 2 off the JM98MAX's row, `Lite` the E30 II Lite off the E30 II's), and one inside its own row's token would rule out the row's own names. One that holds its row's own token (`JM98MAX 2` and `JM98MAX2` beside `JM98MAX`) is how a sibling's longer name is kept off, and stays valid: a positive case pins it, so a later tightening cannot refuse it. The known siblings (`iosKnownSiblings`, B730 B1's follow-up) are iOS PR 1's list as the registry's baseline gives it, in its order (its `knownSiblings`: 24 names in the dump at iOS 6a1241eb that B1 read, and 26 in the dump at iOS 3145606a, which the export's parity has held the catalog's list to since B730 ONIX), and then the siblings a row added past the baseline brings, declared beside it (B944: the ZH3's 16; B958: the iKKO LOT Magic-ARC's 7; so the catalog lists 49): models beside a row's with no row of their own (the E30 II Lite, the JM98MAX 2, the Brooklyn Bridge), kept at the database level as iOS keeps them, and never exported. The lint answers each as the strict matcher does (`strictHits`: a generic name finds no row; then the rows with a port name that is the name, trimmed and its case kept; then the rows holding a token the name holds and none of their excluded tokens, folded; one row is the answer, and two or none answer no row) and refuses one answered with a model row, whose evidence would then be another model's (a family row's name is its siblings' already): by a port name, which the matcher takes before any token and no excluded token rules out, or by a token none of the row's excluded tokens rules out (dropping the E30 II's `Lite` lets both E30 II Lite names reach it). The parity test pins the baseline file by its SHA-256 and runs the strict matcher over the export's keys for every sibling, so re-pinning the export removes no guard; the lint's check is still wanted, because a catalog edit must fail at the lint, before any export or baseline exists. The lint reads no legacy pattern against a sibling, and cannot: the baseline's own rows reach theirs by legacy patterns (the Brooklyn Bridge by `Brooklyn`, the E30 II Lite by `E30 II`), which iOS PR 3 retires, while a row added past the baseline is new and need reach nothing (2026-11-19, backlog B944: the Fosi Audio ZH3 and sixteen Fosi siblings). The export's test, which reads the declarations, holds an added row to the iOS procedure's step 6, both ways against every row: no pattern or token of another row, and no generic name, lies inside its names (its keys and the names its unit reported), none of its patterns or tokens lies inside another row's names (its keys and the corpus names either matcher gives it) or a generic name, folded; through both matchers each of its names is its own and none of another row's is; and each sibling it brings is the catalog's and reached by no row, by a legacy pattern, which the live matcher takes a name by (`firstHit` reads no excluded token, so an exclusion cannot keep a sibling off a pattern, and the pattern is narrowed instead), or by either matcher. In B944's second round that check became `namesApart(corpus, add, x)`, the baseline's corpus passed in, which says each collision as the kind of key it is (`…'s legacy pattern … lies inside …'s name …`, `…'s token …`), since the ZH3's pattern and token are one string and a collision of the one would otherwise read as the other's; the catalog's sibling membership stays in the test that calls it. `TestALegacyPatternSharedWithAnAddedRowIsACollision` refuses what the lint passes, a row that collides with the ZH3 through a legacy pattern alone: a fixture row (`fixture.shared`, its token and port name its own) in the export's rows only, never declared, after the ZH3 with the pattern `Audio ZH3`, inside the ZH3's names, or `Fosi Audio ZH3 Pro`, inside which the ZH3's pattern lies, and before it with `Audio ZH3`, whose first hit takes the ZH3's port, as an earlier row would and give it that row's ceiling and timing; each case asserts one diagnostic, beside a counterpart a character off (`ZH4`) that passes. With the legacy-pattern comparison removed exactly the first two go red, and with the first-hit check on the added row's own names removed exactly the third (the round's controls, in the B944 log entry). **Don't seed a token from a legacy pattern (`KA3`, `TOPPING E30`), hold a row's own token against its own port name, refuse an excluded token that holds its row's own token (`JM98MAX 2`), let a name outside printable ASCII in, let a known sibling reach a model row, by a port name, which no excluded token rules out, or by a token, or keep a sibling off an added row's legacy pattern with an excluded token, which the live matcher never reads: narrow the pattern.** `TestTheIOSNameKeysLint`, `TestNoKnownSiblingReachesAModelRow` (the E30 II's two cases, a Fosi sibling's name as the ZH3's port name and the ZH3's token widened to its maker's name, and the same two for the iKKO LOT Magic-ARC), `TestTheExportMatchesTheIOSBaseline`, `TestAnAddedRowAndEveryOtherRowKeepTheirOwnNames`, `TestALegacyPatternSharedWithAnAddedRowIsACollision` and `TestTheSchemaRefusesWhatItDoesNotDescribe` pin it.
