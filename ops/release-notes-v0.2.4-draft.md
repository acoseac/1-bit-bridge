**The embedded Tailscale node uploads no diagnostic logs unless the config allows it** (backlog B749): in `tsnet` mode the bridge sets `TS_NO_LOGS_NO_SUPPORT=true` for its node unless `tailscale.uploadDiagnosticLogs: true` is set (in `bridge.yaml`, or Settings, Networking), so an install updated from an earlier version stops uploading Tailscale's diagnostic logs, and network flow logs, at its first start of this version: earlier versions uploaded them by default, which is not taken for consent. The node keeps its identity and its state. A tailnet that requires those logs refuses the node until the key is set, and the admin tile says what to change, and, where the key is set and the uploads are off all the same, what holds them off. A `TS_NO_LOGS_NO_SUPPORT=true` in the bridge's own environment keeps the uploads off even with the key set, so allowing them takes removing it as well. A change of the key takes a restart of the bridge's process: once the bridge has run its node with the key off, the uploads stay off until that process exits, so quit the bridge, its menu included, and launch it again, or restart its service (the menu's Start now, and the start `bridge init` offers, run the bridge in the same process). What stays open is backlog B830. The node's name no longer follows the library's: a node already registered keeps the name it has, so a library rename no longer renames it, and a new node registers as `1-bit-bridge` unless `tailscale.hostname` is set.

**Before going back to an earlier version, remove `tailscale.uploadDiagnosticLogs` from `bridge.yaml`** (backlog B749): a bridge from before this release refuses the key at load, whatever its value, and does not start; it also uploads Tailscale's diagnostic logs unless `TS_NO_LOGS_NO_SUPPORT=true` is in its environment.

**An empty Tailscale state file stops the embedded node with the bridge's own explanation** (backlog B828): in `tsnet` mode a `tailscaled.state` that is empty, or holds only white space, as a truncation leaves it, made the node's start fail in Tailscale's words about a TPM-sealed state file. The bridge now refuses that start before it builds the node, whatever `tailscale.hostname` says, and serve's output, `bridge tsnet auth`, `bridge tsnet status` and the admin tile say what to do: put back a copy of the file to keep the node, or move the file aside and restart the bridge, after which the node starts as a new device that authenticates again, takes a new tailnet address and can take a new MagicDNS name. The bridge moves and replaces nothing itself, and a missing state file still starts a new node.
