## The bridge's own player

**DSD after an upgrade: the bridge's own player plays DSD by default, with no approval or first-use step** (backlog B728, B990). On Linux with `output.player` on, the player decides DSD for its DAC from its DSD state, `player-dsd.json` in the data directory, which backups carry. Earlier versions played DSD only under an owner's approval, and never converted it.

- **The default mode.** A DAC with no DSD choice of its own takes the bridge's default mode: `auto`, unless an earlier version's opt-out carried over or the state file didn't read, either of which makes it `off` (both below). Under `auto` the player decides DSD64, DSD128 and DSD256 each from what its DAC catalog says of the DAC, what the DAC offers, listeners' answers, any DoP confirmation on the DAC's current firmware, for DoP the level controls on its playback path, and the choice's cap: native DSD or DoP where the rule admits one, otherwise conversion to PCM (the next paragraph). Section 3 of `ops/plan-b728-dsd-capability-design.md` holds the full rule.
- **A DAC's own choice.** In 0.2.4 a DAC gets one only through `PUT /v1/outputs/{id}/dsd` (below), for the DAC the player is bound to and while the player is stopped; no released app uses it yet, and the console has no DSD control. A choice is kept for the DAC's model from its maker, so every unit of that model shares it.
- **What an earlier version's settings carry over, and when.** `output.player.dsdMode`, `allowDoP` and `dsdQualification` reach the DSD state only through a migration the player's start makes once, and each start of serve warns of each key set. With `dsdMode` unset, whatever the other two say, DSD plays under `auto` from the first start, where 0.2.3 played none: to keep it off, set `dsdMode: off` before the player first starts on 0.2.4. An explicit `dsdMode: off`, or `dop` without `allowDoP: true`, becomes the default, `off`, for every DAC with no choice of its own. `native`, `auto`, or `dop` with `allowDoP: true` wait until the player finds the DAC the binding names. Where the approval record `dsdQualification` names is taken, that DAC gets the mode as its choice, with no rate cap, each approved rate as a listener's clean answer and, for `dop`, or `auto` with `allowDoP: true`, a DoP confirmation, each counting only while the DAC runs the firmware it was approved on; with no record, or one refused, `native` and `dop` become its choice with nothing approved (the next point) and `auto` leaves it on the default. A DAC that already has a choice of its own keeps it. The player paragraph of `config/bridge.yaml.example` gives each key's case.
- **Two carry-overs, as they behave today** (backlog B1042, B1043). An opt-out applies only once the migration has saved it: where that save fails, the start runs without it, under `auto`, and its log says so; if nothing of the save reached the file the next start makes it again, and if it reached the file and its sync failed, that run writes nothing more to the DSD state and the next start goes on from what the file kept. And `allowDoP` false or unset no longer keeps DoP out under `auto`: on a DAC the catalog knows, `auto` plays DoP at a rate the catalog heard it at, or one confirmed on the DAC's firmware, where native DSD isn't offered there or a listener rejected native there, the carrier is offered, every level control on the playback path is at unity, no listener rejected DoP there and the cap allows the rate. An explicit `native`, or `dop` with `allowDoP: true`, whose approval record is missing or refused carries over with nothing approved: it still plays what that mode plays without approval (native DSD the DAC offers, where the catalog knows the DAC or its USB IDs are no generic board's; DoP at a rate the catalog claims, through the level-control check), refuses the rest and never converts to PCM.
- **A state file that doesn't read.** The player then refuses DSD at every rate (`dsd_state_unreadable`) until a DAC's choice is set, and serve's log says which of two cases it met. Where the file reads and doesn't decode (the log says its bytes are kept aside), the bridge has copied its bytes beside it as `player-dsd.json.bad-<time>` and written in its place a new state with the default `off`: move nothing, and set the bound DAC's choice, which ends the refusal, every DAC with no choice of its own staying `off`; where the log says that new state could not be written, the refusal holds in memory alone and the next start tries again. Where the file can't be read (the log says it stays where it is: a read error, a file over 1 MiB, an entry that isn't a regular file, or bytes that couldn't be copied aside), nothing replaces it: move it aside while serve runs, then, with the player stopped, set the bound DAC's choice, which lands with no restart and ends the refusal, the default staying `off`. Until a write puts a new `player-dsd.json` there, a restart finds none and starts afresh, as a fresh install does: the default `auto`, with the earlier version's keys migrated again where `bridge.yaml` still sets them.

**DSD that `auto` plays neither natively nor as DoP is converted to PCM, and under `convert` every DSD rate is** (backlog B728): stereo DSD64 to DSD256, while the bridge has a current reading of the bound DAC, to the highest of 176.4, 88.2 and 44.1 kHz the DAC takes in two channels at 24 bits, or, where it takes none of them at 24 bits, the highest at 16 bits with TPDF dither, at unity gain, and never called bit-exact; for a DAC that takes none of them, those rates are refused (`conversion_not_offered`). Every mode refuses DSD512 (`rate_not_supported`), mono and multichannel DSD and DST-compressed DFF, and while the bridge can't read the bound DAC it refuses DSD (`dsd_dac_unread`). The OpenHome renderer now lists DSF and DFF for controllers when the player can play at least one DSD rate, converted ones included.

**The bridge publishes the bound DAC's DSD choice, and an API changes it while playback is stopped** (backlog B728): `GET /v1/outputs` describes the bound DAC's DSD (`dsdDAC`, and in `dsdPlayback` the rates that play native or as DoP, those converted and those refused, with why), and `PUT /v1/outputs/{id}/dsd` (feature `bridgeDSDChoice`) sets its mode to `auto`, `native`, `dop`, `convert` or `off`, with an optional rate cap (`maxBitRate`) and DoP confirmation (`confirmDoP`): a mode the DAC offers at no rate is refused, and so is `dop` without `confirmDoP` where the DAC offers DoP at a rate that neither the catalog's claim nor a confirmation on its firmware covers. A write is refused with "Stop playback to change DSD" unless the player is stopped (a pause and the console's test tone count as playing); while a write runs, the player starts nothing. `dsdPlayback` no longer sends `qualificationRevision` or `qualifiedOn`, nor `playback` its `qualificationRevision`, which the app already read as optional, and the wire protocol stays at version 1. No released app uses the change route yet.

**The console's Player page plays a test tone** (backlog B601): a 1 kHz sine on both channels, at -30 to -60 dBFS for 5, 10 or 30 seconds, through the DAC while the player is stopped; turn the DAC and the amplifier down first, since the bridge can't see their volume. Stop or leaving the page ends it, and a play from the app or another controller stops it.

**The Player page's transports table follows the DAC's DSD choice** (backlog B1028, B1029): each DSD row is set by the DSD choice that applies to the DAC (its own, which `PUT /v1/outputs/{id}/dsd` changes, or the bridge's default for a DAC with none), the Approved column is now Rates, the rates the player's DSD set plays each way, and a fourth row lists the DSD rates converted to PCM, with the PCM each becomes. The page no longer says DSD comes in a later version, and it still has no DSD control. The example config's player paragraph says where the choice is kept, how it is changed, and that the page has no DSD control.

**A track that fails before it is heard no longer sends Play back to the track before it** (backlog B903AUD): in a gapless queue, when the next track fails while it is being read or decoded, before any of it was heard, playback still stops, and Play from Stopped now starts the entry after the track heard instead of replaying that track. With nothing playable after it (the last track with repeat off, or only tracks already refused), the selection stays where it was. A next track refused before any of it decodes (a missing file, a format the player doesn't play) is skipped, as before, and the one after it plays.

## The web console

**The console's player bar plays to the bridge's own player** (backlog B634): its output button picks this browser or the bridge's player, so the bridge plays to its DAC with no app, wherever the player is on. With the bridge's player picked, the bar plays, pauses, stops, skips, seeks within PCM (not DSD, and not in a window 768 px wide or less), repeats the queue or nothing, and edits the queue as the app does; shuffle, repeat-one and volume are not offered, since the level is fixed. While the bridge's player is running, a switch to this browser asks it to pause, waits up to 10 seconds for it to fall silent, and switches only once it has.

**The console can also be opened on the home network, as an explicit opt-in** (backlog B989): on a loopback install, `adminLANAddress` (or `BRIDGE_ADMIN_LAN_ADDRESS`, or `bridge init --admin-lan-address`) opens it on one private address of the box, at the console's port, with no login and over plain HTTP, to devices on that address's own network (Tailscale's ranges excluded): anyone there can watch it and change the bridge's settings, music and devices. In public mode the bridge refuses that address and does not start. Linux needs kernel 5.7 or later, or 5.0 to 5.6 with `CAP_NET_RAW`; macOS takes an IPv4 address only; and Windows needs every interface of the address's family in the strong host model, with weak host send, weak host receive and forwarding off. Where the listener can't be held to its interface, the console stays on this machine and says why. While the key is in `bridge.yaml`, even empty, 0.2.3 and earlier refuse the file, so an update's automatic rollback to one is not made and one installed by hand does not start: remove the line before going back (the environment variable costs nothing there).

**The console works by touch on phones and tablets** (backlog B1021): with a coarse pointer the player bar's buttons, the Output menu's picks, the queue's entries and Remove buttons, and the breadcrumb links are at least 44 px tall, a window 768 px wide or less gets both times in the player bar, read-only, with no seek, the A–Z rail fits between the bars, and Settings and the duplicates page no longer run sideways on a phone. The bar's controls that can't act say why in words (the Output menu says what the bridge's player doesn't do and what the DAC is handed), and the bar shows the album cover for both outputs (for the bridge's player, in a window wider than 640 px).

**A DSD track says where it plays** (backlog B1021): with this browser as the output, a DSD row this browser can't play and the bridge's player can says so, with its rate and how it would play there (native, DoP or converted to PCM); a row this browser plays as a PCM copy says nothing of the bridge's player. An album's Play, Shuffle and Add are disabled, with the reason in words, when nothing in the edition shown can play in the current output.

**An album held in several editions shows one at a time** (backlog B1023): an album whose folders hold the same songs (a DSD, a hi-res FLAC and a CD folder, say) listed every copy of every song interleaved, and Play, Shuffle and Add took them all. Its page now has a picker with each edition's format and track count, starting on the best edition the chosen output plays, and Play, Shuffle and Add act on the edition shown. Delete still moves the files of every edition (backlog B1036): its confirmation names, whichever edition is shown, each edition whose files it moves, with how many, and each it leaves alone (an SACD image's, or one on an upstream server).

**A Settings save keeps the settings another writer changed in `bridge.yaml`** (backlog B535): at each save the bridge reads the file again under its lock and compares it with the copy it last read or wrote itself, at its start or at its last save. Each setting another writer changed since then is kept as the file holds it, at that save and at every later one until the bridge restarts, rather than written over with the bridge's own copy, and the file's value takes effect at the next start. The save is refused, with nothing saved, and says why and what to do, where it would change one of those settings itself, where the other writer changed `deployment`, or where the file that writer left, or the one the save would write, would not load at the next start.

**The upload page runs one upload at a time** (backlog B797): while an upload, a resume or a retry runs on the page, its pickers, drops, Upload, Try again and Discard are refused and the drop zone says why, so two uploads from one page no longer disturb each other's progress or files. The hold is the page's own: another tab still lists a running upload as interrupted.

**The console's lists keep your place and filter by name** (backlog B1021): Back to a list, or its crumb, returns to the row you left, past the first page and after a jump on the index rail too, and a list whose restored rows start past its first row offers Back to the top. Albums (a genre's and a composer's albums included), Artists, Genres, Composers and Playlists take a filter that narrows the list by name (an album by its title or its album artist), its count with it, and its rail and pages where it has them (Genres have no rail, and Playlists come in one page). In Safari, a tap during or just after a long scroll no longer goes nowhere.

**Every album sort has an index rail, and a finger can drag it** (backlog B1021): Recently Added, the sort Albums opens on, gets a rail by the date it sorts by (this month, earlier this year, then each year), which is when the album's tracks were last indexed, not a first-seen date, so an album every track of which a scan rewrites files under this month; Year gets one by year or by decade, and Title and Artist keep their letters, as the artists' and composers' lists do. On a touch screen the rail is one column at least 44 px wide, as tall as the room between the bars (in a window 500 px tall or less, a grid of seven columns), which takes a drag and shows where the list is in a callout beside the finger.

## Setup, CLI and doctor

**An update counts as healthy only once it has answered and stayed up for 10 minutes** (backlog B660): until then the install stays on probation with `.bak` kept, and after three starts of the new version that did not end cleanly (a stop, a restart, or a listener the host refuses to bind ends one cleanly), the next start puts the previous version back and exits 75 for the service manager to start it; where it may not, `bridge doctor` fails and serve's log says why, as the Probation row in Settings → Updates does where the start could record it. A migration of the database rules that rollback out, and this release migrates it the first time it opens it (schema 60 to 62): the upgrade notes below say the way back.

**On Windows the updater waits out a moment's hold on the bridge's binary** (backlog B898): a real-time scanner holding the binary could leave a failing release in place after a rollback, or no binary at all. Before it moves anything, the updater now waits up to about 5 seconds for a sharing or lock violation on the binary, its backup or the new version to clear, never for access denied, and it retries putting a binary it moved aside back for about 3 seconds. `bridge restore` reads a busy snapshot's manifest again for up to about a second, on a sharing violation or access denied, before it asks you to confirm, and refuses one still busy by asking you to run it again shortly (exit 1), rather than calling it unrecognized (exit 2).

**On a Windows Service install, `bridge logs` and `bridge doctor` read the Service's own log** (backlog B618): run from a shell, they looked under the shell user's folder, so they read or graded a log the bridge never writes. Where the install kind can't be told, they read the Service's log if it is there, else the user's, and say which; the doctor says the log wasn't checked only where neither is there.

**Snapshots are verified as they are taken** (backlog B653): each snapshot records every file's size and SHA-256, and a check gives its database (SQLite's `quick_check` and its schema) and its other files a verdict each, which `bridge doctor` and the console (Jobs, Settings → Backups) show; `bridge backup --verify <snapshot-dir> [--full]` checks one again, and `bridge backup` now exits 0 only when both verdicts are `VERIFIED` (the database's `UNVERIFIED` where the install has no database yet) and recorded. `--verify` checks only a snapshot in the configured install's backups folder: a copy elsewhere is refused (exit 2), though `bridge restore` takes one. A snapshot taken before 0.2.4 records no sizes or hashes, so `--verify`, with `--full` or without, only checks that its files are there, opens no database, reads `UNVERIFIED` and exits 1. Retention keeps the newest snapshot whose database verified beside the `keep` newest. Checks and prunes need a file lock in the backups folder: on storage that grants none, no check, prune or scheduled snapshot runs while the newest waits for its check (`bridge doctor`'s `backup-lock` line says so), so keep the data directory on a local disk or a share whose lock service runs.

**`bridge backup` prunes by the config's retention** (backlog B1035): without `--keep` it now keeps what `backup.keep` (or `BRIDGE_BACKUP_KEEP`) says, as serve's scheduled snapshots and the console's do: `-1` keeps every snapshot, 0 or none the default 7, and `--keep N` overrides it for one run (0 or less keeps every one). Before, it kept the seven newest whatever the config said, so where the config keeps more, or every one, a snapshot taken before the update with 0.2.3's `bridge backup` takes `--keep 0`.

**`bridge restore` refuses while a bridge command has the library open** (backlog B653, B826): it refuses, with nothing restored, while any bridge command (`scan`, `analyze`, `upscale`, `library add` or `remove`, `backup`, `doctor`) has the database open, while a check or prune of those snapshots still holds them after a short wait, and on a data directory whose storage grants no file locks. Stop first every process of an earlier version and any other program that has `bridge.db` open (an `sqlite3` shell, say), since those take no lock restore can see. A snapshot on read-only media, on storage without file locks or in a folder you can't write is refused with nothing restored: copy its folder to a local disk and restore from the copy.

**`bridge doctor` no longer hangs on a library root whose mount stopped answering** (backlog B650): each step that touches a root gets 5 seconds, a root that doesn't answer fails `library-roots` by its configured name, and every other check finishes, in the CLI and the console's doctor alike. The bound starts once the doctor has found and read `bridge.yaml`: where `bridge.yaml` itself lies inside a root whose mount stopped answering (the next line's layout), the doctor waits on it before any check.

**The doctors, `bridge init`, the console and the log say when `bridge.yaml` or the data directory lies inside a library root** (backlog B884): a library root is often a mount, and while one stops answering, every command that reads inside it waits on it, serve and the doctor included. The console says it in its doctor, on the Diagnostics page, and the check compares the paths as written, so a link, a junction or a bind mount between them isn't seen. Nothing is refused; on a managed bridge the doctor and the Diagnostics page leave the warning out.

**`bridge init` that keeps a config prepares the data directory first** (backlog B664): before it installs or starts the service, it checks the data directory the service will use, as serve does, and makes it, and where serve would refuse it exits non-zero with the reason, the config unchanged. Before, the service failed at its working directory (systemd's 200/CHDIR, restarting every 2 seconds) while init exited 0.

**Commands refuse a data directory whose volume reads as away** (backlog B727, B741): every command that makes, opens or writes the data directory now refuses it, exit 1, as serve does, when the recorded data directory reads as not mounted, reads of the library such as `bridge duplicates` included; `bridge doctor`, `status`, `logs`, `token list`, `cert info` and `update --check` still run, and a data directory moved on purpose needs `dataDir`. Serve also writes an identity into the data directory, `data-dir-id.json`: leave it there, move it with the data directory, and run commands as the user the service runs as. A data directory refused for holding no identity that is the right one, its volume mounted, is taken as serve's own again once the record beside the config, `.bridge.yaml.datadir`, which the refusal names, is removed, a `data-dir-id.json` that doesn't read moved aside first.

**A config lock the bridge can't use names its remedy** (backlog B537): a `.bridge.yaml.lock` this user may not open to read and write (another user's, as a `sudo` run can leave it, or one whose mode refuses it) now says what to do: give it the config file's owner with owner read and write, or remove it while the bridge is stopped and no bridge command runs.

**`bridge init --force` keeps the enrichment mirrors and opt-outs, and a Settings save keeps what only the environment changed** (backlog B617, B761): a rewrite keeps non-default `enrich.musicbrainzBaseURL` and `enrich.coverArtBaseURL`, and the enrichment switches and the update check written off; the rest of `enrich`, `fingerprint` and `atlas` is written at its defaults, as before. A console save no longer writes a `BRIDGE_*` variable's value into `bridge.yaml` for a setting left as it was, and Settings says the environment wins at the next start.

## Networking and the app

**The embedded Tailscale node uploads no diagnostic logs unless the config allows it** (backlog B749): in `tsnet` mode the bridge sets `TS_NO_LOGS_NO_SUPPORT=true` for its node unless `tailscale.uploadDiagnosticLogs: true` is set (in `bridge.yaml`, or Settings, Networking). `BRIDGE_TAILSCALE_UPLOAD_DIAGNOSTIC_LOGS`, where it is set (an empty value leaves the key's), overrides the key both ways: `true` allows the uploads with no key, and `false` keeps them off over a true key. The shipped `compose.yaml` forwards it from `.env`, and a change of it takes `docker compose up -d`, which recreates the container: `docker compose restart` keeps the old environment, so a consent changed to `false` would leave the uploads on. So an install updated from an earlier version, with neither set, stops uploading Tailscale's diagnostic logs, and network flow logs, at its first start of this version: earlier versions uploaded them by default, which is not taken for consent. The node keeps its identity and its state. A tailnet that requires those logs refuses the node until the key or the variable allows them, and the admin tile says what to change, and, where the key is set and the uploads are off all the same, what holds them off. A `TS_NO_LOGS_NO_SUPPORT=true` in the bridge's own environment keeps the uploads off even where the key or the variable allows them, so allowing them takes removing it as well. A change of the key takes a restart of the bridge's process: once the bridge has run its node with the key off, the uploads stay off until that process exits, so quit the bridge, its menu included, and launch it again, or restart its service (the menu's Start now, and the start `bridge init` offers, run the bridge in the same process). A stop of the bridge that gives up waiting for its node's start, with the setting on, turns the uploads off until that process exits too: no new upload starts after it, and the admin tile says so (backlog B830). The node's name no longer follows the library's: `tailscale.hostname`, where it is set, names the node, registered or new; without it a node already registered keeps the name it has, so a library rename no longer renames it, and a new node registers as `1-bit-bridge`. Where the node's state is there and can't be read, the start can't tell whether the node is registered, gives it the library's name as earlier versions did, and its log says so.

**An empty Tailscale state file stops the embedded node with the bridge's own explanation** (backlog B828): in `tsnet` mode a `tailscaled.state` that is empty, or holds only white space, as a truncation leaves it, made the node's start fail in Tailscale's words about a TPM-sealed state file. The bridge now refuses that start before it builds the node, whatever `tailscale.hostname` says, and serve's output, `bridge tsnet auth`, `bridge tsnet status` and the admin tile say what to do: put back a copy of the file to keep the node, or move the file aside and restart the bridge, after which the node starts as a new device that authenticates again, takes a new tailnet address and can take a new MagicDNS name. The bridge moves and replaces nothing itself, and a missing state file still starts a new node.

**Enrichment can be switched off** (backlog B617): `enrich.enabled: false` (Settings, or `BRIDGE_ENRICH_ENABLED`) stops within a second every MusicBrainz, Cover Art Archive and Deezer request, a mirror's included, the Atlas premium lookup and AcoustID fingerprinting; `enrich.deezerEnabled: false` (or `BRIDGE_ENRICH_DEEZER_ENABLED`) stops the Deezer artist photos alone. What was fetched is still served; the Atlas harvest's cover fetches stop with the switch, and the rest of the harvest, its lyrics, the update check and Let's Encrypt go on. While enrichment is off, a cover or artist photo still waiting for enrichment answers 404 `no_image` instead of 202 `pending`, and manifests carry no `enrichmentProgress`.

**The update check can be switched off** (backlog B761): `update.checkEnabled: false` (Settings → Updates' Check for updates, or `BRIDGE_UPDATE_CHECK_ENABLED=false`) stops every request to GitHub's releases API and every install (Check now, Install, `bridge update`, auto-install), while the status, Roll back, a start's rollback and a new version's probation still run. `/v1/health` advertises no update while it is off, and `bridge update` reads the key as the service does, so an off set only in the service's environment must be in the shell's too.

**The bridge indexes WavPack and Monkey's Audio files and serves them as they are** (backlog B489): `.wv` files (a hybrid one's `.wvc` correction file kept as part of it, never a track of its own) and `.ape` files are scanned, tagged and served unchanged, never transcoded, and the manifest and search list them only to an app that declares it plays them (`X-Bridge-Formats: wavpack, ape`; iOS 2.3), so today's app doesn't index them. Analysis, upscaling, DLNA and the bridge's own player leave them out for now; the console lists them, with their download, and plays neither; with fingerprinting on, fpcalc reads their audio for AcoustID as it does any track's.

**A Christmas smart mix** (backlog B750): a mix named Christmas is served from 1 December to 5 January (UTC) to an app whose view of the library holds at least 15 Christmas tracks across 3 albums or 3 artists (a WavPack or Monkey's Audio track counting only for an app that declares its format), found by genre, album title, carol titles and Christmas words in a title, never by artist. The console marks it out of season the rest of the year, and an app shows it as any other mix, which its Settings can hide.

**Host names that aren't ASCII are used in their IDNA form** (backlog B744): a `customEndpoints` entry or `autocert.domain` that isn't ASCII is now certified and published in its `xn--` form, `bridge init --domain` writes that form and says so, and a name that has none is refused where it is typed (`bridge init --domain`, or a custom endpoint saved in Settings); before, the certificate could not be made. One already in `bridge.yaml` still loads: a custom endpoint with none is dropped with a warning, and an `autocert.domain` with none is served as `autocert-domain.invalid` with a warning, so the bridge runs under a public name that works nowhere until it is corrected. A library name also loses its control characters wherever it is set.

**The embedded Tailscale node moves to 1.104.5, among the dependency updates**: Tailscale 1.104.2 to 1.104.5, the SQLite driver 1.61.0 to 1.62.0, quic-go 0.64.1 to 0.65.0, golang.org/x/crypto 0.58.0 to 0.59.0 and golang.org/x/image 0.47.0 to 0.48.0, with x/term and x/mod; Go stays 1.27.3. Tailscale 1.104.5's netstack turns RACK loss recovery off unless `TS_NETSTACK_ENABLE_RACK=true` is set, which may slow recovery for tsnet transfers on paths that reorder packets.

## Fixes

**The first scan after the update reads every file's tags again** (backlog B743, B489, B428): ExtractorVersion moves from 30 to 33, so files already indexed are re-read once, and rows that come out unchanged are not sent to apps again, but for an SACD image's tracks, which every move of ExtractorVersion rewrites: those are sent again and queued for enrichment again.

**A track number written with a total is read** (backlog B743): a Vorbis `TRACKNUMBER` or `DISCNUMBER` (a FLAC's, say) written `1/2`, `3 of 12` or ` 3 ` was indexed as 0 (a track number as the file name's leading number, where the name began with one), so its album could play out of order; it now reads the leading number, and an ID3 tag's ` 3 ` is read too.

**An album's tracks in one folder share one year** (backlog B756): an album whose tracks carried different recording years showed as several albums in the app; each track not at its folder's most common recording year now takes it (a tie goes to the later year), a track with no year or a year before 1877 (a composition date) included, and editions in separate folders stay apart. An album whose tracks carry only years before 1877 keeps them, a track with no year taking the most common one. The first full scan after the update rewrites the rows, and serve runs one at its start.

**An M4A's work tag is read** (backlog B428): the bridge now reads `©wrk`, and a freeform `WORK` under `com.apple.iTunes` that its tag reader missed, as the iOS app reads both, so a file whose work is in `©wrk` groups under it from the bridge as it does in the app over SMB; where a file's `WORK` and `©wrk` differ, the bridge takes the `WORK`.

**A lost waveform can be drawn again when it is asked for** (backlog B652): a curve gone from the waveform directory stayed missing (`/v1/waveform` answered 410) until `bridge analyze --force`, or a change of its source, analysed the track again. Now that request, which still answers 410, can ask for the curve to be rendered again in the background while analysis is on. The repair holds off while the whole directory looks lost (missing, unreadable, empty, or short of at least ten curves and more than a fifth of them), and stops after two failures of its own until the file or the bridge's build changes.

**A library root whose volume isn't mounted refuses writes, and is watched again once it mounts** (backlog B776, B777): an upload or a trash restore into a root the bridge has indexed tracks under is refused while the root reads as not mounted (409 `root_not_mounted`) with nothing written, and the console's Try again resumes the same upload once the volume is back. A root the bridge has indexed nothing under yet gives the check nothing to go by, and takes the write. A volume mounted over a root the bridge was already watching is watched again, checked every 30 seconds.

**The player checklist no longer points MPD at the bridge player's DAC** (backlog B1022): its DAC line (console and `bridge doctor`) told a reader to set MPD to the DAC the bridge's own player drives, which ALSA gives one player at a time. While the player is on, the line now names no card for MPD. The console's line matches the two by ALSA card: MPD set to the player's card is a warning, and the line reads OK where MPD is set to another card, or to none while the player's DAC is the only one; `bridge doctor`, which can't see the player's card, warns that it can't tell which DAC the player uses.

**A stop during serve's start ends it cleanly** (backlog B662): a stop that arrived while serve seeded its upscale target could end it with exit 1 and a database error (`sql: transaction has already been committed or rolled back`).

## Upgrade notes

**Nothing puts 0.2.3 back for you once 0.2.4 has run: the way back is by hand** (backlog B660, B1037): once 0.2.4 has opened its data directory, as its first start does once its settings load, the console's Roll back refuses, and so does the crash rollback, which puts the previous version back after three starts of the new one that did not end cleanly, once 0.2.4 has begun to migrate the database (schema 60 to 62), as that start does. There are two ways back.

- **The binary alone, the default.** It keeps everything that changed since the update, devices paired since included. Stop the bridge, remove this release's new keys from `bridge.yaml` (the next two lines), switch `update.autoInstall` off if it is on, since 0.2.3 can install 0.2.4 again at a later check, and put the 0.2.3 binary in place of the bridge's: the updater's backup beside it, the binary's name with `.bak` added, until the start after 0.2.4's install is confirmed removes it, or else the 0.2.3 release's archive (with Docker, the `0.2.3` image on the same volume). Then start it. 0.2.3 opens and serves the migrated database as it stands, since it runs no migration step it lacks, and lists to every app the WavPack and Monkey's Audio tracks this release indexed until its scans drop them. It reads neither `player-dsd.json` nor `data-dir-id.json` and leaves both for a later 0.2.4: its player plays DSD as it did before the update, by `dsdMode`, `allowDoP` and the approval record, and no DSD choice set in 0.2.4 applies there. Its first start may say that it won't roll back to `.bak` because 0.2.4 opened the data directory, and clears the install it read.
- **A snapshot from before the update, only to have the schema-60 database back.** A restore writes the snapshot's database, `bridge.yaml`, tokens and TLS pair back as they were, so it undoes every change made since the snapshot, devices paired since included. Retention keeps a pre-0.2.4 snapshot only among the `keep` newest once a newer one has verified (about a week at the defaults), so copy its folder out of the backups folder if you may want it. In this order: stop the service and every other program using the database; remove this release's new keys from the live `bridge.yaml`, which 0.2.3's restore loads; put the 0.2.3 binary in place, as above, and run **its** `bridge restore` (0.2.4's opens the restored database to mint its backup epoch, which migrates it to 62 again, and while a failed start's install waits for its confirmation it can refuse before copying anything); check the restored `bridge.yaml`, the snapshot's, for this release's keys, and switch `update.autoInstall` off in it; then start the service.

**Before going back to an earlier version, remove `tailscale.uploadDiagnosticLogs` from `bridge.yaml`** (backlog B749): a bridge from before this release refuses the key at load, whatever its value, and does not start; in `tsnet` mode its node also uploads Tailscale's diagnostic logs unless `TS_NO_LOGS_NO_SUPPORT=true` is in its environment.

**Before going back to an earlier version, remove this release's other new keys from `bridge.yaml`** (backlog B617, B761, B989): a bridge from before this release refuses `enrich.enabled`, `enrich.deezerEnabled`, `update.checkEnabled` and `adminLANAddress`, whatever their value, and does not start, and an update's automatic rollback is not made while one is there. Switching enrichment, the Deezer photos and the update check back on in Settings removes a key that turns one off; a key that holds `true`, or one a `BRIDGE_` variable overrides so that Settings already shows it on, stays and takes removing by hand, as `adminLANAddress` does, and `tailscale.uploadDiagnosticLogs` has the line before this one.

**Reload any console tab left open across the update** (backlog B1029, B1037): a page loaded from 0.2.3 keeps running 0.2.3's script, and the Player page's no longer reads the player's status: where it shows the player's transports, it says "Couldn't read the player" at each refresh until it is reloaded.
