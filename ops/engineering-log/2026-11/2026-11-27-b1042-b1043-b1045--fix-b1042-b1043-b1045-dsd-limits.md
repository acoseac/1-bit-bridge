### B1042, and B1043's part 1: a migration takes effect for its run when its save fails

**The hazard, on production's routes at 29df3a4a.** A 0.2.3 bridge set `dsdMode: off`, or `dop`
without `allowDoP: true`, which the migration also turns off (29df3a4a `migrate.go:175-176`). The
first 0.2.4 start migrates it, and where the write of `player-dsd.json` fails:

- before it lands (a full disk, an I/O error), serve ignored `migrate`'s error
  (`cmd/bridge/serve_player.go:516`), said "the migration of the legacy DSD keys was not saved,
  and the player starts without it" (29df3a4a `serve_player_dsd.go:310`), and the store kept
  what it held, `Defaults()`, `auto`;
- once it lands and its barrier fails (`atomicwrite.ErrLanded`), the store recorded the fence and
  returned without holding the new state (29df3a4a `store.go:344-352`), so the running player used
  `Defaults()` too while the file said `off`.

Either way that run played DSD under `auto` where the operator had opted out. With 0.2.3's `auto`
and no `allowDoP: true`, the same windows left no marker in memory, so B1043's rule (below) could
not see the opt-out for that run.

**The fix.** `dsdstate.Store.Migrate` hands its write `heldIfFailed` for the start step alone,
the step with no DAC bound (`internal/player/dsdstate/store.go:414`), and `updateLocked` holds the
state that step made where its write fails, landed or not (`store.go:363-365`): its marker and its
default, which `Store.State` publishes and the effective policy reads at each refresh. Serve and
`bridge output play` both make the step through it (`cmd/bridge/serve_player.go:516`,
`cmd/bridge/output_play.go:263`), so both get it.

- Landed and not durable: the fence stays (`store.go:361`), every later write is refused with
  `ErrLandedNotHeld`, and the file already holds the same state.
- Not landed: nothing is at the name, and a later write of the run (a user's choice, playback's
  evidence, the DAC's part) is made from the held state, so it persists the marker with the
  default. A migrated `defaultMode: off` never reaches the file without its marker: a marker-less
  `off` would outlive a later edit of `bridge.yaml` with no warning, since `Migrate` assumes
  `auto` wherever the marker is absent (`migrate.go:164-180`).
- The next start reads what the file holds: none, and it migrates again as before; one with the
  marker, and the migration is done, as after a successful start.
- A part of a DAC's keeps its behaviour: its failure is not held, the marker keeps waiting, and
  `playerDSD.retry` asks it again (`TestADACPartsRefusedWriteIsAskedAgainInThisRun`, unchanged).
  A step refused before its write holds nothing (`TestADACPartWhoseWriteFailsIsNotHeld`).

Serve's line for the start step stays a Warn line and names the default the run plays by
(`cmd/bridge/serve_player_dsd.go:321`, `defaultMode=off`): "was not saved, and the player holds it
for this run alone". Its words had said "the player starts without it", which the hold makes
false; the landed line said the same and now says the player holds it for the run
(`serve_player_dsd.go:328`); a step refused before its write, which holds nothing, keeps the old
words (`serve_player_dsd.go:315`). Three other texts claimed the store does not hold what landed,
false for a landed start step now: the store's error (`store.go:82`), the migration's fence line
(`serve_player_dsd.go:308`) and playback's evidence line
(`internal/player/playback/dsd_policy.go:1064`) drop that clause and keep the rest, the words
`internal/alsapcm`'s count matches among it. The docs of `Store.State`, `Update`, `Landed`,
`playerDSD.done`, `say`, `steps` and `waits` say the same.

### B1043: a 0.2.3 `auto` without `allowDoP: true` keeps DoP out until a user consents

**The hazard, on production's route at 29df3a4a.** 0.2.3 ran `output.player.dsdMode: auto` with
`allowDoP` false or unset, so it never played DoP. The B728 design's migration table, its `auto`
row (`ops/plan-b728-dsd-capability-design.md` §3.6), said DoP "stays out, unacknowledged and
unconfirmed, until the app acknowledges its first use". B990 dropped first use, and with it that
step: 0.2.4's `auto` played DoP on a catalog-known DAC at a rate the catalog heard DoP at with no
native there (29df3a4a `internal/player/policy/policy.go:637-638`).

**The rule.** The marker already records 0.2.3's keys (`MigratedFrom`: `DSDMode`, `AllowDoP
*bool`; `internal/player/dsdstate/migrate.go:169-173`), so no state field is new.
`policy.reading.dopKeptOut` (`policy.go:708-715`) is true while the marker is `from: keys` with
`dsdMode: auto` and `allowDoP` not true and the DAC holds no DoP confirmation a user wrote for its
current, readable firmware: `SetBy` not `migration`, and its `BCDDevice` the bound unit's readable
bcd, as `d.Confirmed` compares it (`policy.go:565`). `decide`'s `auto` branch reads it once a plan
(`policy.go:642`) and asks it before the known sub-branch's DoP (`:647`) and the unknown one's
(`:654`). So mode `auto`, the DAC's own choice or `defaultMode`, converts what it would have played
DoP, or refuses it as `conversion_not_offered` with no target. A consent under other firmware lifts
nothing, though `d.Heard` would admit DoP there. A user's `auto` write without `confirmDoP` keeps
DoP out; one with it writes the confirmation (`internal/player/policy/choice.go:181-183`), and
DoP plays. An `auto` write with `firstUseAcknowledged` alone keeps DoP out, and its acknowledgement
covers what `auto` then plays (`autoTransports`, `choice.go:254`): native, the firstUse readback
saying `native acknowledged, dop pending`. `dop` is no `auto`: a confirmed `dop` wrote a consent,
which a switch back to `auto` keeps; an unconfirmed `dop` the catalog's claims admitted gave none,
and the switch back restores the block. Out of scope, as the brief decided: a marker with `dsdMode`
unset (0.2.3 played no DSD, and the 0.2.4 default applies), no marker, and native.

**The read side keeps its meanings.** `options.dop.needsConfirmation` stays "a rate an explicit
`dop` write would need `confirmDoP` at" (`PROTOCOL.md` 1109, 1323; `choice.go:155`), and
`allowDoP` "a profile claim or a user confirmation" (`internal/player/playback/dsd_view.go:46-51`,
`:219-223`): `dopKeptOut` changes no `DoP` fact the view reads, and the rule shows only through the
effective plan, `dsdPlayback.tuples`, `converted` and `refused`. No wire field, warning code or
`PROTOCOL.md` byte changes.

### B1045: a migrated 0.2.3 approval keeps its DoP rates

**The hazard, on production's route at 29df3a4a and v0.2.3.**

1. On 0.2.3 the player ran with `dsdMode: dop`, `allowDoP: true` and a `dsdQualification`
   record that approved DoP at DSD64 only. 0.2.3's record holds approved policies alone, each a
   tuple at its rate (v0.2.3 `internal/player/qualification/approval.go:58-70`), and 0.2.3
   refused DoP at a rate the record did not approve (v0.2.3
   `internal/player/playback/authorization.go:263-264`).
2. The first 0.2.4 start migrates it into a clean DoP answer at each approved rate (29df3a4a
   `internal/player/dsdstate/migrate.go:271`) and, since the record approved some DoP rate, one DoP
   confirmation with no rate, tied to the firmware (`migrate.go:282-283`;
   `internal/player/dsdstate/state.go:173-180`).
3. 29df3a4a `policy.go:559` counted that confirmation at every rate. Under `dop` (29df3a4a
   `policy.go:663-676`), and under `auto` with `allowDoP` on a known DAC (29df3a4a
   `policy.go:637`), a rate with no other DoP evidence played DoP where 0.2.3 refused it. The
   carrier, gain and firmware checks do not show that the DAC decodes DoP there; on one that does
   not, the brief computes from DoP's framing that the track plays as noise, about -57 dBFS in the
   audible band plus an ultrasonic line near -27 dBFS (an estimate taken from the brief, not
   measured here).
4. It was deliberate since B990: `TestServeOutputPlayAllowDoP` expected a DoP64-only record to
   play DoP at 2822400 and 5644800 (29df3a4a `cmd/bridge/serve_player_dop_test.go:346-349`,
   `:358`, `:366`). The owner chose to narrow it.

**The fix.** It narrows only what a confirmation the migration wrote grants:

- `d.Confirmed` takes `&& (c.SetBy != dsdstate.ByMigration || d.Clean)`
  (`internal/player/policy/policy.go:565`). `d.Clean` is computed before it (`policy.go:545`)
  from `rd.listener` (`policy.go:420-430`), the latest DoP answer at this rate whose `BCDDevice`
  is the unit's readable bcd, and none while the bcd does not read: the clean DoP answer at this
  rate on this firmware. So the migration's confirmation counts at its record's approved rates, or
  where an independent clean answer has come since, clean evidence at a rate authorizing it; its
  `Confirmed` field says so (`policy.go:243`), and the policy's package doc's third point.
- The catalog keeps its authority as B990 designed it: a rate the row hears or states still admits
  DoP under `dop`, and a heard one under `auto`, and a row that states DoP to DSD256 still plays
  DSD128 DoP. The residual, a maker-stated DoP that a unit does not decode, belongs to the
  catalog's evidence rules (B730), not here.
- A user-written confirmation (the app's or the console's) keeps counting at every rate. A user's
  `confirmDoP` replaces a migrated confirmation: `choice.go:181` adds
  `|| d.DoPConfirmed.SetBy == dsdstate.ByMigration`, for app and console writers alike, and
  `Choose`'s doc says so (`choice.go:113-117`). Before it a confirmed `dop` write over the migrated
  `dop` kept the migration's confirmation, which after the narrowing would still leave DSD128
  needing a confirmation the user had given. `choice.go:155`, which reads the per-rate `Confirmed`,
  needs no logic change.
- Native is out of scope: no noise path.

**The read side.** `dsd_view.go:189-190` does not change: `choice.dopConfirmed` keeps
`PROTOCOL.md`'s meaning (1100-1101: "whether the DAC's DoP confirmation counts on its current
firmware"), since a new meaning would need a `PROTOCOL.md` change and its iOS mirror before the
iOS 2.3 archive. So a migrated confirmation can show `dopConfirmed: true` beside

**A start step past the state's bounds (B1042).**

1. At 872d157a `updateLocked` returned the encoding's error before `hold` (872d157a
   `store.go:348-351`), and `encode` runs the state's check and then its size bound. A start step
   whose state with its marker and warning encoded past the 1 MiB the file may hold
   (`maxFileBytes`, `state.go:108`) was refused with nothing held: the run played under `auto`.
2. A start step over a state holding the 512 warnings a state may hold (`maxWarnings`,
   `state.go:111`) appended `migrated_off` as a 513th (872d157a `migrate.go:177-178`), which the
   check refused, "more than 512 warnings": `off` lapsed the same way.

The fix (7a6e7c80):

- `updateLocked` holds a start step's state refused as `ErrTooLarge` (`store.go:354`), as a write
  that did not land: nothing is written, a later write of the run that makes the state smaller
  saves it with its marker and default, and one that does not is refused alike, the held state
  kept. Any other refusal of the encoding is a state the check refuses and is never held, so the
  store never publishes a state its own check refuses.
- The start step writes no `migrated_off` into a state at the cap (`migrate.go:205`): the opt-out
  goes without its warning, and the state stays one the check takes.
- `playerDSD.say` says the step was not saved because the state would pass the 1 MiB its file may
  hold, that the player holds it for this run alone, the default it plays by, and that a later
  write that makes the state smaller saves it (`serve_player_dsd.go:326`).

### Round 3: a time the reader takes and the writer refuses no longer defeats `dsdMode: off`

**The hazard, checked at 328064fa before anything changed.**

1. Go 1.27.3's `encoding/json` reads an RFC 3339 time whose offset is 24 hours or more and will
   not write one. Its strict parse is off and falls back to `Parse`
   (`time/format_rfc3339.go:155-170` in the toolchain's source), which takes an offset's hour up to
   24 and its minute up to 60 (`time/format.go:1273-1276`); the writer refuses an hour past 23,
   "timezone hour outside of range [0,23]" (`time/format_rfc3339.go:62-76`). Measured with a
   scratch program on this toolchain: `+24:00`, `-24:00`, `+23:60` and `+24:60` read and do not
   write, `+25:00` does not read, `+23:59` reads and writes as itself, and `+00:60` reads and
   writes as `+01:00`.
2. The state's reader asked a time nothing but whether it was zero (328064fa `state.go:827`,
   `DAC.check`; `:957`, `Warning.check`), so `Store.Open` loaded such a file
   (`store.go:175-182`).
3. The migration's start step over it, a 0.2.3 `dsdMode: off`, made off and its marker, and
   `updateLocked` failed at the encoding (328064fa `store.go:348`) with `json.Marshal`'s error,
   which is not `ErrTooLarge` (`:354`): nothing was held, the store kept the markerless `auto`, and
   serve and `bridge output play` played native DSD at every rate the kernel offered.
4. `ForRestore` (`restore.go:36-56`) took such a snapshot as a state: for a time it keeps, its
   rewrite failed and so did the restore; for an observation it drops, it installed the state
   without it.

**The fix (3d4b879d), as decided in the brief.** The reader refuses a time its writer cannot write.
`writable` (`internal/player/dsdstate/state.go:1011-1014`) marshals the time alone, its offset
kept, through `json.Marshal`, as `encode` does. `DAC.check` asks it of `choice.setAt` (`:845`),
`dopConfirmed.confirmedAt` (`:857`), a first use's `acknowledgedAt` and `observedAt` (`:878`,
`:880`) and an evidence entry's `driverAcceptedAt` and `streamingObservedAt` (`:921`, `:923`), and
`Warning.check` asks it of `at` (`:994`). `checkAt` runs both for schema 2, and for schema 1 before
`fromSchema1` drops its DAC entries, and every writer of either schema marshalled its file through
`encoding/json` (13a388be, B728 B3, the first, `json.Marshal`). A time a file leaves out reads as
the zero time, which the writer writes. The file is then damaged, kept aside and replaced by
`Refusing`, over which the start step migrates nothing, and DSD is refused as
`dsd_state_unreadable`; a restore installs such a snapshot as its bytes. The state's whole
encoding is not asked at the read: a denser file than the writer's own still reads and its restore
still fails `ErrTooLarge`. The start step's hold stays `ErrTooLarge`'s alone: as the brief decided,
the other errors of an encoding are a state structurally invalid.
