## 2026-11-26 — B1035: `bridge backup` takes its retention from the config unless `--keep` is given

### Why

At 0a8d39f3 `bridge backup` registered `--keep` with a default of 7 (`cmd/bridge/backup.go` 62), handed that flag to the prune (`Keep: func() int { return *keep }`, 101) and to its report (`kept %d most recent`, 130), and never asked the config it loads (83) for a retention. Serve's ticker prunes by `liveCfg().Backup.EffectiveKeep()` (`cmd/bridge/main.go` 4611), and the console's create by `cfg.Backup.EffectiveKeep()` unless its request names `keep` (`internal/admin/handlers_backups.go` 255), which neither console button does (`internal/admin/static/app.js` 5299 and 6307 post no body). So an operator who turned retention off (`backup.keep: -1`, which `docs/backup.md` described) or kept more than seven, and ran `bridge backup --config <file>` before an upgrade or a move as the guide and the README say to, lost every snapshot past seven. The item's measurement: eight runs with `keep: -1` left 3, 4, 5, 6, 7, 7, 7, 7 snapshots, and 0.2.3 behaves alike. At 0a8d39f3 this entry's test made eight runs with `keep: -1` and found seven left.

No caller relied on the command's default: `run()` hands it the command line (`main.go` 3014), and every other execution path prunes by the config already.

### The fix

After the config loads, the command resolves one retention (`backup.go` 93 to 101 at 22ce2c11): `retain := cfg.Backup.EffectiveKeep()`, replaced by `*keep` where `fs.Visit` saw `--keep` on the command line. The prune (`Keep: func() int { return retain }`) and the report (`res.Prune.Deleted, retain`) both read it. The flag is registered with no default (`fs.Int("keep", 0, …)`), since Go's flag package prints a non-zero default as `(default 7)` in `-h`, which would have read as the retention a run without the flag applies; the flag's help and a second line under the usage line say that it overrides the config's `backup.keep`. `--verify` is as it was: it returns before the config loads, and a `--keep` beside it is ignored.

What each value means, unchanged and now the command's too: the config's `-1` (any negative) is retention off and `0` or none the default, 7 (`EffectiveKeep`); the flag's `0` or less is off, as before. `BRIDGE_BACKUP_KEEP` is derived from the field (`internal/config/env.go`) and applied by Load, so the precedence is an explicit `--keep`, then the variable, then the file. The orphan sweep runs with retention off whichever way it is off (`internal/backup/backup.go` 1334 to 1337).

### What else changed

- `docs/backup.md`: the intro says each run prunes by the configuration's retention; the retention paragraph says which retention the command applies, the precedence, the `-1` and `0` values, and that a `bridge backup` before 0.2.4 pruned to 7 without `--keep`, so an older version's run before an upgrade takes `--keep 0`. It no longer says retention is on for "`backup.keep` above 0", which read 0 as off.
- `internal/config/config.go`, comments only: `BackupConfig` said its knobs only govern the in-process schedule, now `IntervalHours` alone does; `Keep`'s and `EffectiveKeep`'s say the retention is every snapshot's; Validate's note said any non-positive value disables pruning, where 0 is the default.
- `.claude/rules/cli-serve.md`: the rule, one line.
- Unchanged: the README describes no `--keep`. The deployment runbook's `--keep` lines are the deploy table's pre-deploy snapshots, `bridge backup --keep 0` run by the old binary, which keeps every snapshot then and now. `PROTOCOL.md`'s backup paragraph (`[--keep N]`, the ticker's `keep: 7`) says nothing this makes false, and it is mirrored in the app's repository.
