### 1. A pairing request reads its endpoint list before it writes a token

On `a79c69b2` the mint (`apiTokensMint`) and the rotation (`apiTokensRotate`) took `Server.mu`,
minted or rotated the token (`Auth.Mint`, `Auth.Rotate`) and only then built the QR's
alternates, through `pairAlternates`, which called the provider (`Deps.Endpoints`, the API's
`ReachableEndpoints`) with no context. That provider's Tailscale status read waits behind
another caller's at the API's status cache's lock, up to its own bound: a request that ended
there kept the console's lock, and had already written a secret nobody was shown.

The handlers read the list first now, after their body's checks and before the lock
(`pairingEndpoints`, waited for through `endpointsWithin`, as the console's endpoint list is),
and hand it to `pairAlternates`, which takes the list. A request that ends while the list waits
returns with nothing minted, rotated, issued or answered; the shared read runs to its end and
is cached for every caller. A public bridge, and a listen address with no port, read no list,
as `pairAlternates` consulted none there. `advertisedEndpoints`, the anchor of the "nil is no
list" rule, is what `endpointsWithin`'s goroutine calls.

`TestAPairingRequestThatEndsWhileItsListWaitsChangesNoCredential` runs the mint and the
rotation, each with the API's shared status read held (the real `api.Server` beside the
console, its tailnet in tsnet mode): the handler returns at its request's end having answered
nothing; no token is made or rotated and no code issued (a counting code store); the rotated
token's secret still validates and its code from before still redeems for it; the read, still
held then, is let go, returns once, and `/v1/health`'s list carries the tailnet's name it
found.

- Red first, at `bd3e5917` (the base's code): both cases failed at "did not return when its

### 2. A panic of the endpoint list's provider has one reporter

On `a79c69b2` the provider's goroutine logged a recovered panic only where its request's
context had ended at the recovery, and without its value. A cancellation landing after that
look and before the hand-off left the panic neither raised nor logged; one landing before the
recovery while the caller had yet to choose between the answer and the context's end could
have it logged and raised both.

One claim decides it now, an `atomic.Bool` both sides compare and swap: the goroutine claims the
answer for the caller as it hands it over, and the caller claims it for the goroutine as it
stops waiting at its context's end. Where the hand-off comes first the caller raises the panic
again, whichever arm its select takes, and nothing logs it; where the caller's claim comes
first, the goroutine logs it, its value under `panic` beside `stack`, the stack read at the
recovery. A list handed over once the context has ended is dropped for the context's error.
`endpointsWithin` became a method of the console's server, its steps seams on the server
(`testEndpoints`: the caller's choice, the goroutine just before its claim, and the
goroutine's end), and its line's words no longer say the panic came after the request ended.

- Red first, at `cdabed48` (the seams on the old logic): `TestAPanicAfterItsRequestEndedIsLoggedWithItsValue`
  red at the value alone; `TestAPanicWhileItsCallerWaitsIsRaisedAgainAndNotLogged` green (the
  half the old logic had right); `TestACancellationBetweenTheRecoveryAndTheHandOffIsReportedOnce`
  (the goroutine held before its claim while the request ends) red, reported by neither;
  `TestAPanicReadyBesideTheRequestsEndBeforeTheChoiceIsReportedOnce` (the caller held before
  its choice while both become ready, sixteen rounds) red in its first round, reported by both.
- Controls on `a1b3b3e2`: the context's look put back at the recovery, the claim deciding only
  the hand-off (the brief's): the forced interleaving red, reported by neither, and the
  both-ready case red, reported by both; the other two green. The caller returning at its
  context's end without its claim: three red (the both-ready case in its round 6, where the
  select took the context's end). The value dropped: the two logging cases red at it. The stack
  read before the provider runs: the same two red at the stack, which must name the provider's
  panicking frame in `endpointsWithin`'s goroutine.

### 4. The live Windows table test reconciles its readings

`TestTheStrongHostModelIsReadFromTheStack` compared four separate observations of a family:
the interfaces and their names (read once, before both families), the interface table, each
row's own entry (an error at once on a difference) and each interface's addresses. An
interface that gained an address between the table and the addresses failed a correct reading.
Each attempt now reads all four again, up to three (`hostModelAttempts`), and a mismatch fails
only once the attempts are spent: a bounded reconciliation of separate observations, not an
atomic snapshot. The set of interfaces that must have rows takes an address of the family as
`*net.IPNet` or `*net.IPAddr`: Go's Windows reading gives an anycast address as the second
(`src/net/interface_windows.go`, its walk of `FirstAnycastAddress`, in Go 1.27.3), which
escaped the set.

The reconciliation and the set are `reconcileHostModel` and `addressOfFamily`, in a test file
every platform builds, driven by injected readings: both address types in both families
(`TestTheExpectedSetTakesBothAddressTypesInBothFamilies`), a mismatch that settles on the
second attempt (`TestAMismatchThatSettlesOnTheSecondAttemptIsNoMismatch`), one that persists
past exactly the bound (`TestAPersistentMismatchIsTheReadingsOnceTheAttemptsAreSpent`), and a
table that does not read ending it at once.

- Controls: `*net.IPNet` alone: the expected-set case red in both families, and, beyond the
  prediction, the settling case too, whose first reading's mismatch is the anycast-only
  interface's missing row. The bound one short: the persistent case red at its count. No
  retry: the settling and persistent cases red.
- This host cannot run the live test: it was compiled for windows/amd64 and windows/arm64

#### A pairing request ended at the console's lock

At `378f2285` both handlers read the endpoint list on the request's context, then waited for
`Server.mu`, then called `Auth.Mint` or `Auth.Rotate` with no look at the context. A request
cancelled while it waited behind another pairing write still minted or rotated, a rotation
ending the old secret and its code with nobody shown the new ones; and a request already ended
went straight to the write down the paths that read no list (a public bridge, no provider, a
listen address with no port), where `pairingEndpoints` and `endpointsWithin` return without
asking the context.

Each handler now looks at its request's context once it holds the lock, and returns answering
nothing where it has ended: it writes no response and returns no error, so round 1's wording
that the handler returns its context's error was wrong and the long form no longer says it.
The lock is taken through `lockPairingWrite`, whose hook on the server
(`testPairingWriteWaits`, the player writes' pattern) tells a test the write found the lock held,
which comes only after its list was read. The guarantee is that look's: a request whose context
has ended when the handler acquires `Server.mu` performs no credential mutation. After it,
`Auth.Mint` and `Auth.Rotate` take their own lock and persist with no context, so a cancellation
during that later wait can still precede a write; nothing here promises that every cancelled
request writes nothing.
