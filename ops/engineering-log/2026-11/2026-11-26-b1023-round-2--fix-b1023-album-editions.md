### What changed

All in `static/player/views.js` and `player.css`; `format.js`'s one export, `output.js`, the server and the album's JSON are as they were.

- **Deletions by their paths.** A path a trash request carries reads Deleting… until the request answers (`trashing`, the module's, so a pick, a regrouping and a redraw of the album all keep it), and the answer (`settleTrash`) reaches the album page shown now (`albumShown`, each render's, its generation checked), which reads the album again. A file the trash moved never comes back on the page. One it could not move is the album's again where a read begun after that answer lists it (`deletions`, by album and path, with the answer's count), so a file moved back stays, playable, and one left in the trash goes with its retired row. A rejection that is `postJSON`'s Error is the trash's refusal, which the handler makes before it moves anything (`trashManager`, the body's decode, `Trash`'s own refusals), so nothing moved; fetch's TypeError, or an answer whose body does not read, leaves every path it carried unknown, held off the page for the page's life with a line saying how many and how to see what the library holds, since the move can land after any read the page makes. A read after an answer that fails leaves what it could not settle held until a read succeeds.
- **What an inconclusive read shows.** After a lost answer the page lists only rows whose fate it knows: a read that still lists the held paths (the move had not landed, or never will) keeps them off and says so; one that no longer lists them says nothing of them. A reload is a new page, which shows what the library holds.
- **One edition again.** Whether the page shows editions is asked at each paint. An album a deletion leaves with one edition has no picker, its Delete asks in the album's words, its stat line is its rows' own, and an SACD image's tracks are never offered to Delete, on every album page.
- **When `{album: id}` is safe.** The server expands an album's id from the catalog's `TrackPaths`, which list a moved file until the catalog is built again (the post-delete scan's nudge), and where its row's retirement failed (it runs on the request's context) the file's row stays in the store. So the page sends an album by its id only while it shows one edition and has recorded no deletion of that album; from the first answer that took one of its paths off the page it sends the paths it shows, until the page is loaded again. A render of an album whose answers moved nothing (both moved back) goes by its id again.
- **The slot.** `watchOutput` subscribes once to the output's own view and lets the slot go at each change of the output in effect, an album page open or not.
- **The rows' bounds.** Where the page sends the edition as its paths, `trackList` takes the list a title would send to the bridge's player's bounds once a list (`fitsTheBridge`), and `downloadCell` a row's own path (`fitsAPath`): a title past them sends nothing (`aria-disabled`, named by the page's words, `album-scope`), a row's Add past them is disabled and named the same, and Play and Add to queue name the count line beside those words where both apply. A source filter's list is its own: an edition past the bounds whose filtered list fits sends that list from the row tapped. Other pages (favorites, playlists, mixes) and an album sent by its id pass no bound, so their rows send as they did.
- **The fold.** The disc-folder rule mirrors `discNumberForFolderName` exactly: the keyword's letters as `unicode.ToLower` folds them (a dotted capital I is an i and the Kelvin sign a k; a long s and a dotless i are no letters of it, which JavaScript's `/i` already holds), between Go's white space (U+0085 is, U+FEFF is not). The tie-break compares lengths and order in UTF-8's bytes.
