## Bugs

### B1 · [Medium] Deduped enqueue counted as enqueued → second overlapping batch stuck `running` forever
`internal/transcode/batch.go:459-556` (Submit) + `batch.go:792` (SubmitOptimize) · **Confidence: High** · verified end-to-end.
`Pool.Enqueue` returns `nil` for *both* a real enqueue (`pool.go:426`) and a dedup hit on an in-flight `(source,variant)` (`pool.go:393-396`). `Submit` seeds **all** candidate paths into `state.RemainingIDs` (`batch.go:418-420`) and does `enqueued++` for every `nil` return (`batch.go:555`), with no filter for paths already live in another batch (`batch.go:330-361`). The in-flight job carries only the **first** enqueuer's `BatchID`, so `OnJobComplete`/`OnJobFailed` delete the path only from *that* batch's `RemainingIDs` (`batch.go:983`/`1029`) — there is no cross-batch reconciliation. Trigger: operator re-submits the same folder+target (or a parent folder) while the first batch's jobs are still in-flight (variants not yet committed, so `HasVariant=false` still includes them). Every overlapping path dedups → never callback'd for batch 2 → `allDone` (`len(RemainingIDs)==0`) never fires → batch 2 sits `running` forever, inflating `Throughput().EtaSeconds`. Self-heals only on restart via `RecoverInterruptedBatches`. Audio is unaffected (batch 1 produces the variants); this is stuck bookkeeping/UI. **Fix:** make `Enqueue` signal dedup distinctly (sentinel `ErrDuplicateInflight` or `(enqueued bool)`), and in the Coordinator drop deduped paths from `RemainingIDs`/`TotalFiles` instead of counting them.

### B2 · [Medium] Key/tempo analyzer lacks the NaN/Inf guard its two siblings have → bogus "C major" committed permanently
`internal/analyze/keytempo.go:143` (`add`) · **Confidence: High** (code inconsistency + committed outcome traced; trigger is the same non-finite-decode class the siblings already defend).
`loudnessMeter.addFrame` sanitizes NaN+Inf (`loudness.go:134`) and `peaker.add` sanitizes NaN (`waveform.go:36`) — both for the corrupt-decode class (PR #463). `keyTempoAnalyzer.add` buffers `float64(s)` with **no** finite guard. A non-finite mono sample (e.g. float WAV/AIFF NaN/Inf payload passed through sox `-e float`; note `hann[0]=0` turns `Inf*0` into NaN in `processWindow`) poisons `a.chroma` for the track. In `estimateKey`, `sum` is then NaN, so the `sum <= 0` no-estimate gate is bypassed (`NaN <= 0` is false, `keytempo.go:197`); every `pearson12` returns NaN; `c > bestCorr` is always false, so `bestRoot/bestMajor` keep their inits → returns `(0,"major",true)`. `analyze.go:218-220` commits that confident bogus **C major** to `AnalysisRow.KeyRoot/KeyMode`, keyed to mtime+size so it is never re-analyzed. **Fix:** in `add`, `if math.IsNaN(float64(s)) || math.IsInf(float64(s),0) { s = 0 }` before buffering (guard both, unlike waveform's NaN-only).

### B3 · [Low] Batch row persisted outside `c.mu` with no monotonic guard → cancel-vs-completion reorder can wedge DB row non-terminal
`internal/transcode/batch.go:948` (`transitionStatus`) + `batch.go:1004`/`1053` (job callbacks) + `internal/manifest/store.go:4087` (`UpdateUpscaleBatchStatus`) · **Confidence: Medium**.
All three snapshot the row under `c.mu` but `persistBounded(...)` runs **outside** the lock, and `UpdateUpscaleBatchStatus`/`UpdateUpscaleBatchProgress` are unconditional `UPDATE ... WHERE id = ?` (store.go:4078/4096) with no `updated_at`/terminal guard, so the last write to reach `Store.mu` wins regardless of logical order. Interleave: a non-terminal `OnJobComplete` snapshots `{running,processed:k}` and unlocks; a concurrent `Cancel`→`transitionStatus` snapshots `{cancelled}`, deletes the batch from `liveBatches`, unlocks; the two persists (different goroutines: HTTP handler vs publisher) reorder so `cancelled` lands then `running` lands last → DB stuck `running`, batch gone from `liveBatches` (no callback will correct it). Narrow window (only while cancelling a live batch as a completion lands); self-heals on restart. **Fix:** persist inside `c.mu`, or add `WHERE updated_at <= ?` / a terminal-status guard so a stale non-terminal write can't overwrite a terminal one.

### B4 · [Low] `Delete` of an Approved-but-unpolled row drops it without revoking → unrevoked orphan token in auth.Store, no log
`internal/pairing/store.go:515-521` · **Confidence: High** on mechanism; legit flow is correct.
The guard at `:515` only catches `StateExpired && TokenID != ""`. A `Delete` on a still-`StateApproved` row that already minted `TokenID` (approved, token never Poll-delivered) falls through to `expiryTimer.Stop()` + `delete(s.byID, id)` — the undelivered-revoke timer is cancelled and the row dropped, but `auth.Store` is never told to revoke. The minted token stays valid while its raw value was never delivered (it lived only in the just-deleted row). A correct iOS client only DELETEs *after* a successful Poll, so the legit path is fine (Delete==ack, token is now the client's bearer). The leak needs a buggy/hostile pollSecret holder DELETEing before its first Poll → an unusable-but-valid token entry that nothing will revoke and nothing logs (unlike the `maxRevokeAttempts` give-up path, which logs). Low severity (no auth bypass — raw value undeliverable), but a hygiene/observability gap. **Fix:** if `State==StateApproved && TokenID != ""`, route the delete through onTimer's revoke-then-drop path, or at minimum log the dropped `TokenID` for operator reconciliation.

### B5 · [Low] `estimateKey` has no minimum-correlation gate → confident key for atonal / flat-chroma tracks
`internal/analyze/keytempo.go:201-218` · **Confidence: Medium** (may be a deliberate best-effort choice).
`estimateKey` gates only on `windows >= minWindowsForKey` and `sum > 0`; it never checks the winning correlation strength. Because `bestCorr` starts at `math.Inf(-1)`, any non-silent chroma returns `ok=true` — even a flat chroma (every `pearson12` returns 0 via the `da<=0` branch, picking root 0 "major"). Percussion-only / atonal sources therefore get a confident key the package docblock says to suppress ("fall back to 'no estimate' rather than guessing"). Only affects the estimated-key field when the source carries no key tag, so blast radius is small. **Fix:** after the rotation loop, `if bestCorr < minKeyCorrelation { return 0,"",false }` (small positive threshold ~0.1–0.2). Flagged Medium-confidence because the omission may be intentional best-effort behavior — confirm intent before changing.

### B6 · [Low] `resolveReleaseGroupMBID` doesn't negative-cache a persistent 404 → album siblings re-issue guaranteed-404 MB lookups
`internal/enrich/enricher.go:890-897` · **Confidence: High** on mechanism.
The helper returns on *any* `ReleaseGroupMBID` error without caching (comment: "Do not negative-cache on error — transient network failures should retry"). But that blanket rule also skips caching a **persistent** `IsNotFound` 404 (`musicbrainz.go:295`), which MB returns when the embedded release MBID is unknown. Called per-track (`enricher.go:773`) with a `hint` short-circuit only when an rg-MBID was already resolved; so an album whose release MBID is known but whose release-group 404s, with no rg-hint, has every sibling track (all sharing that release MBID via `albumCache`) miss `releaseGroupCache` and re-issue the identical guaranteed-404 lookup, each paced at `MBMinInterval` (1.1s) — ~N×1.1s of MB budget burned per pass on a lookup that can never succeed. This is the exact "N-track spin" class the *album-level* `SearchRelease` path already guards (transient→uncached, persistent→cache-empty); this helper makes no such distinction. Bounded: within one pass only (the tracks get `MarkEnriched` regardless), and re-triggered only on an operator enrichment-reset. **Fix:** `if err != nil { if IsNotFound(err) { e.releaseGroupCache.Set(releaseMBID, "") }; return "", err }` — negative-cache the persistent 404, leave transient errors uncached.

### B7 · [Low] `Scan` doesn't guard on `ctx.Err()` before the deletion pass — a cancelled full scan is reported clean and stamps `last_full_scan`
`internal/manifest/scanner.go:425-428` · **Confidence: High** on the asymmetry.
After the walk drains (`close(paths)`→`workersWG.Wait()`→`close(writes)`→`writerWG.Wait()`), `Scan` checks only `if walkErr != nil`. `walkErr` is non-nil only if the *walker* observed cancellation; a `ctx` cancel during the `Wait` window (clean walk already done) leaves it nil, so `Scan` runs the deletion pass, stamps `s.lastFull.Store(now)` + `SetScanState("last_full_scan", …)` (scanner.go:518-519), runs the reconciliation passes, and returns `(count, nil)`. `ScanSubtree` (scanner.go:1204) has exactly the guard `Scan` is missing — and its comment literally claims *"`Scan` does the same"*, which is false. Data integrity is safe (`seen` is complete since the walk finished, so no wrongful reap; store ops fail-fast on the cancelled ctx), but a cut-short full scan is indistinguishable from a completed one and the dashboard's "last full scan" advances. **Fix:** add `if ctx.Err() != nil { return int(committed.Load()), ctx.Err() }` before the deletion pass (mirror ScanSubtree:1204); fix the stale ScanSubtree comment.

### B8 · [Low] Watcher's debounced `ScanSubtree` dispatch is untracked → can race `Store.Close()` on shutdown (SQLite-corruption class)
`internal/manifest/watcher.go:232-245` + `cmd/bridge/main.go:1804` · **Confidence: Medium** · watcher is OFF by default.
The `AfterFunc` callback checks `if ctx.Err() != nil { return }` (:238) then calls `ScanSubtree(ctx, dir)` — a TOCTOU: `scanCancel()` can fire between the check and the scan. `cancelAllPending` (:253) only `Stop()`s *un-fired* timers; a timer already past its ctx check isn't stopped. main.go runs `watcher.Run(scanCtx)` in a bare `go func()` with **no WaitGroup**, and the `AfterFunc` dispatches are tracked by nothing — so an in-flight watcher `ScanSubtree` (mid `UpsertTrackBatch` transaction) can run while `defer manifestStore.Close()` executes. This is the exact class the documented "graceful shutdown waits for `bgScans` WaitGroup / prevents SQLite corruption" invariant guards — but that WG covers admin/periodic scans, not the watcher's `AfterFunc` layer. **Fix:** track dispatched callbacks in a `sync.WaitGroup` (Add before `AfterFunc`, Done at callback end), `Wait()` it in `Run`'s cancel branch after `cancelAllPending`, and have main.go wait for `Run` to return before `Store.Close()`.

### B9 · [Low] `isWatchLimitError` folds `EMFILE` ("too many open files") into the watch-limit path → wrong operator remediation hint
`internal/manifest/watcher.go:283-291` · **Confidence: High**.
The marker list matches `"too many open files"` (EMFILE/ENFILE — a file-descriptor exhaustion) alongside `"no space left on device"` / `"watch limit reached"`, all routing to the single degrade-to-periodic path whose log hint tells the operator to raise `fs.inotify.max_user_watches`. But fd exhaustion needs `ulimit -n` / `fs.file-max`, not `max_user_watches` — so an operator who actually hit the fd cap is sent to the wrong knob (and a transient fd spike is treated identically to the permanent watch-budget case). The fallback *behavior* (periodic-only) is fine; only the hint is wrong. **Fix:** split the classification — give the fd-exhaustion marker its own message pointing at the open-files limit.

### B10 · [Low] Truncated WAV/AIFF body short-read aborts before the folder-`cover.jpg` fallback → track loses its cover art
`internal/manifest/extractors_aiff_wav.go:360-363` (and the ID3/COMM/LIST body reads) · **Confidence: High**.
A short read on any chunk body `return`s the error, which `extractByFormat` propagates, so the walker returns *before* the tail `extractLocalArtwork(absPath, t, …)` call (:377-379). Concrete input: a WAV truncated mid-`fmt ` chunk sitting in an album folder that contains `cover.jpg` — the track is still indexed (scanner writes it with `Codec="WAV"` + path-derived metadata, logging the error at `Error`) but the folder-level cover fallback is skipped, so that one track shows no art. The MP4 sibling (`extractMP4WithContext`) doesn't have this shape — it catches walker errors at Warn and still reaches its local-artwork path. Only triggers on already-truncated/corrupt files. **Fix:** on a body short-read, log at Warn and `break` out of the chunk loop (fall through to the `extractLocalArtwork` tail) rather than `return`ing.

### B11 · ⭐ [High] Four reconciliation passes don't exclude UPnP-routed rows → perpetual re-enrich / delta-churn / split-album loop on hybrid libraries
`internal/manifest/scanner.go:585, 606, 635, 656` · **Confidence: High** · traced end-to-end. **Top finding of the audit so far.**
`runAlbumArtistReconciliation` (:585, writes `AlbumArtist`), `runYearReconciliation` (:606, writes `Year`), `runAlbumTitleReconciliation` (:635, writes `Album`), and `runYearReconciliationByMBID` (:656, writes `Year`) all stream `StreamTracks(ctx, nil, …)` with **no routed-row exclusion** and write the reconciled field back into `tags_json` (bumping `indexed_at`). But `walkFieldsEqual` (ingest.go:500-504) compares exactly `AlbumArtist`, `Album`, and `Year`. The loop on the documented hybrid deployment (fs roots + a Chord 2Go UPnP upstream, 15,283 routed rows): (1) fs `Scan` reconciles a routed album whose per-track values disagree (the exact split-album case reconciliation targets — `buildTrackAndRouting` stamps per-track `AlbumArtist = w.Artist`), writing the dominant value + bumping `indexed_at`; (2) the next UPnP walk loads its baseline from `tags_json` (reconciled value) so `walkFieldsEqual(existing, fresh)` is **false** (fresh carries the original per-track value); (3) the row is re-upserted via `UpsertTrack`, which **resets `enriched_at = 0`** and overwrites the reconciled field back to the raw value + bumps `indexed_at` again. Net: the minority-tagged routed tracks flip-flop every fs-Scan / UPnP-walk cycle — perpetual MB/CAA/Deezer re-enrichment treadmill (the exact churn PR #369 eliminated, re-opened via the reconciliation vector), iOS delta-sync re-receives them every cycle (the "iOS freeze" class), and split-albums resurface. Silent (no error). **The fifth pass, `runTrackNumberReconciliation` (:695), already has the exact fix** — a fail-closed `UPnPRoutedSourcePaths` exclusion with a comment citing PR #370 and *"would fight the ingest's skip-if-unchanged reconcile"* — it simply was never back-ported to the four older passes. **Fix:** add the same routed-row exclusion (fail-closed on the fetch error) to all four passes; or hoist it into the shared streaming helper so every reconciler inherits it.

### B12 · [Medium] `/v1/health` computes UPnP upstream counts uncached → unauthenticated LAN flood drives an O(routed-rows) COUNT per request
`internal/api/api.go:1505-1506` + `cmd/bridge/upnp_upstream_public.go` · **Confidence: Medium**.
Every other DB-backed field on the unauthenticated `/v1/health` handler is shielded by a short TTL cache for flood resistance — `healthCountsCache` (3s + singleflight), `reachabilityCache` (5s, api.go:1494-1496), `cachedTailscaleStatus` (5s). `PublicServers(r.Context())` is the exception: it runs uncached on every request, and the production adapter loops the configured upstreams issuing `CountUPnPRoutingForServer` → `SELECT COUNT(*) FROM upnp_track_routing WHERE server_udn = ?` per server. On the documented local-Mac + Chord 2Go deployment (15,283 routed rows), an on-LAN unauthenticated `/v1/health` flood drives a ~15k-entry index scan per request per server — the exact cost the sibling caches exist to bound. (Public-mode bridges are exempt — UPnP upstream is `Validate`-rejected there.) **Fix:** wrap `PublicServers` in a small TTL cache mirroring `healthCountsCache`, or cache the per-server counts in the adapter.

### B13 · [Medium] UPnP ingest skip path returns with `res.ServerUDN == ""` → admin per-server telemetry is lost for healthy (skipped) upstreams
`internal/upnpingest/ingest.go:265-271` · **Confidence: High**.
On the skip path (the common steady-state — the SystemUpdateID gate exists precisely to skip most ticks), `res.Skipped = true; return` fires before `res.ServerUDN = udn` (set only at ~:273, after the gate). The admin adapter keys its per-server telemetry map on `res.ServerUDN` (`cmd/bridge/upnp_upstream_admin.go` `lastByUDN[pr.ServerUDN] = pr`), so every skipped result is stored under key `""` (colliding all skipped servers, last-writer-wins), while `ConfiguredServers` looks rows up under `StableServerKey(srv)` — never `""`. Result: a correctly-functioning, up-to-date (=skipped) upstream shows **no recent-walk telemetry** on the newly-shipped admin "Sources" dashboard (PR #510). **Fix:** move `res.ServerUDN = udn` above the `decideSkipWalk` early-return.

### B14 · [Low] `statusWriter.Flush()` (void) shadows `FlushError()` → SSE disconnect-detection via `rc.Flush()` is dead code
`internal/api/middleware.go:151` · **Confidence: High**.
`statusWriter` implements a void `Flush()` but not `FlushError() error`. Every SSE handler wraps it in `http.NewResponseController(w)` and relies on `if err := rc.Flush(); err != nil { return }` to notice a dead client (events.go:69/82/112, pairing.go:298/331/357). But `ResponseController.Flush()` unwraps to the *first* `http.Flusher` it finds — `statusWriter` itself, via this void `Flush` — before it can reach the underlying HTTP/2 writer's `FlushError()`, so it always returns `nil`. That disconnect branch can never fire. (Proof of the mechanism: `statusWriter` deliberately does *not* implement `SetWriteDeadline`, so `boundedHandler`'s `rc.SetWriteDeadline` correctly unwraps through `Unwrap()` — only the flush path is shadowed.) Not a leak in practice — disconnects still surface via `writeEvent`'s `Write` error and `ctx.Done()` — but the code reads as if flush errors are handled. **Fix:** add `func (s *statusWriter) FlushError() error` delegating via `http.NewResponseController(s.ResponseWriter).Flush()`.

### B15 · [Low] Variant-delete `FreedBytes` overcounts when the sidecar was already gone
`internal/api/upscale_delete.go:455` · **Confidence: High**.

### B47 · [Medium] UPnP proxy follows redirects → SSRF: a rogue LAN upstream can make the bridge fetch its own no-auth admin API and relay it
`internal/upnpproxy/proxy.go:248` · **Confidence: High** · verified.
`defaultClient()` builds an `http.Client` with a custom Transport but **no `CheckRedirect`**, so the stdlib follows up to 10 redirects automatically. `Serve` fetches a `<res>` URL from an SSDP-discovered upstream (a LAN device — potentially rogue, or an attacker who spoofs SSDP for a configured UDN's `LiveHost`) and relays the **final** response body. A malicious upstream answering the fetch with `302 Location: http://127.0.0.1:7789/api/…` (or `169.254.169.254`, RFC1918) makes the bridge — running on the host — fetch its own loopback-only, no-auth admin console and relay those bytes to the requester. `/dlna/file/{trackID}` reaches this path **unauthenticated** (LAN bind), so a LAN attacker gets a server-side-request-forgery + info-disclosure primitive that defeats the loopback-only admin protection. It also violates the package's bit-exact contract (a 3xx should be relayed verbatim, not consumed server-side). The codebase already applies this exact defense in `internal/enrich/deezer.go`'s `installRedirectGuard`. **Fix:** set `CheckRedirect: func(*http.Request, []*http.Request) error { return http.ErrUseLastResponse }` so 3xx are relayed verbatim and never followed to internal hosts. (Preconditions: UPnP-upstream feature enabled + a rogue/spoofed LAN server — hence Medium not High.)

### B49 · [Low] systemd unit escaper doesn't escape `$` → an install/config path containing `$` breaks `ExecStart`

### B52 · [Low] Playlist-cover filename uses a lossy sanitizer → two distinct playlist ids collide to one file (cross-playlist cover mixup)

## Larger refactors

### L1 · Scan tail runs five full-library reconciliation passes on every scan (incl. idle 6h ticks)
`internal/manifest/scanner.go:518-560` · **Confidence: Medium**.
The scan success tail issues five sequential full-library `StreamTracks` passes — `runAlbumTitleReconciliation`, `runAlbumArtistReconciliation`, `runYearReconciliation`, `runYearReconciliationByMBID`, `runTrackNumberReconciliation` — each a full `SELECT … variantsAggSQL … ORDER BY path` scan with the dependent variant/analysis CTEs, each building its own full `[]ReconcileTarget` slice, on *every* scan including each 6h periodic tick when nothing changed. On a 50k-track / 5k-folder library that's five redundant full-table streams + five whole-library allocations per scan. (`UPnPRoutedSourcePaths` is also fetched twice per scan — the deletion pass at :449 and again in a reconciliation pass.) The streaming-not-materializing discipline is correct; the *repetition* is the cost. **Fix:** feed all five reconcilers from a single `StreamTracks` pass into the shared `ReconcileTarget` slice, then run the pure reconcile functions — preserving the ordering constraint (album-title must precede album-artist). Confirm each reconciler currently does its own stream before consolidating.

### L2 · `Config.Validate()` mutates its receiver — a sharp edge on the copy-on-write contract
`internal/config/config.go:1664` · **Confidence: High**.
`Validate()` is used as a load-time check but is NOT a pure predicate — it rewrites `Enrich.*BaseURL` (:1713), `Autocert.Domain` (:1801), and `CustomEndpoints` (:1888) on its receiver. Every current caller validates a freshly-loaded config or a `config.Clone(cfg)`, so it's safe today. But it's a footgun on the `RuntimeConfig` COW contract: a future caller doing `rc.Load().Validate()` on the *published* snapshot would mutate a shared `*Config` in place, racing concurrent per-request `Load()` readers (the exact torn-read the atomic holder exists to prevent). **Fix:** split the normalization into an explicit `Normalize()` step (called before `Store()`), leaving `Validate()` a pure predicate; or at minimum document "never call on a published snapshot" on the signature.

### L3 · Atomic-write persist sites don't fsync the parent directory → config/state writes aren't crash-durable
`internal/config/config.go:2224` + every `atomicwrite.RenameWithRetry` caller · **Confidence: Medium**.
`Save` (and the auth/updater/adminauth/backup persist sites) fsync the temp file's *bytes* but never fsync the parent directory after the rename (`RenameWithRetry` is a bare retry-loop around `os.Rename`). On a crash/power-loss immediately after the rename, the directory-entry update can be lost even though the file bytes were durable — leaving the old file (or, on some filesystems, a dangling entry). It IS atomic w.r.t. concurrent readers (the stated goal), just not crash-durable. This is a codebase-wide pattern, so it's a one-place fix. **Fix:** add an optional parent-dir fsync inside `atomicwrite` (open dir → `Sync` → close) after the rename, so every persist site inherits crash-durability. (Weigh against the extra fsync cost on frequently-written state files.)
